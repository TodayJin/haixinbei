# 任务编程（上位机可编程状态机）设计

> 目标（用户原话，m17516）：**"任务车只是一个执行机构，具体流程都是上位机搞的"** ——
> 上位机拼任务 → 存成二进制程序 → 烧进车的 Flash → 车离线自主执行。
> 多个任务、每个任务多个状态模块、每个状态模块内部用基础块拼；主页负责常态循迹与状态切换。

## 0. 三个待用户确认的决策（本文档按此定案，用户可否决）

| 决策 | 取的值 | 备选 |
|---|---|---|
| 执行位置 | **程序存车上 Flash、车离线自主跑**（比赛不能遥控；上位机只负责编辑/烧写/监视当前状态与块号） | 上位机在线逐条解释下发（实现快，但比赛时必须有上位机连着） |
| 基础块 v1 | **8 类块 + 9 类条件**（见 §3），不含变量/分支/循环 | 加变量、if/else、块内循环（表达力强，代码量与出错面大一圈） |
| 状态内部结构 | **状态 = 顺序块序列 + 可选"进入块"**；主页 = 常态循迹状态；收尾用「跳到状态」或「结束」 | 状态内再套一层子状态机（界面多两层） |

## 1. 数据模型（上位机视角）

```
Task          任务：名字 + 若干状态 + 指定哪个是主页
  └ State     状态模块：名字 + enter 块序列（进入时跑一次）+ body 块序列
      └ Block 基础块（叶子）：一个动作 / 一个等待
```

- **主页（main）**：任务的入口状态，通常就是"常态循迹"。任务启动后从主页面开始跑。
- 其它状态是"插进来的模块"（过障碍、爬坡、倒库…）。任何状态都能用 `跳到状态` 切走，
  干完活再 `跳到状态(主页)` 回到常态循迹。
- 一个车辆可存**多个任务**；任选一个启动。

## 2. 执行语义（固件侧解释器）

- 5ms 一拍、**全非阻塞**（旧 `renwu.c` 有 210 处 `HAL_Delay()`，新系统一个都不用）。
- 进入状态：先顺序跑 `enter` 块（跑完），再顺序跑 `body` 块；`body` 跑到底没有跳转 = 状态停住
  （最后一块必须是「跳到状态」或「结束」，上位机编辑器会校验这一点）。
- 块分两类：**立即块**（执行完立刻进下一块）与**等待块**（每拍查条件，满足/超时才进下一块）。
- 任何时刻只有一个状态在跑；`跳到状态` = 立刻切换（不等待），进入新状态重跑它的 enter 块。
- 任务结束（`结束` 块）或出错停机：`Motion_Stop()` + `SpeedControl_Stop()`。
- 遥测回传：`当前任务号 / 状态号 / 块号 / 该块已运行 ms / 超时标志`（上位机据此高亮正在跑的那一块）。
- **安全**：程序运行期间**不**受上位机链路看门狗约束（比赛要离线自主）；`T_CMD_STOP`、
  `T_TASK_STOP`、急停仍然随时能停。

## 3. 基础块与条件（v1）

### 3.1 块（10 字节定长，见 §4）

| op | 名字 | 参数 | 语义 |
|---|---|---|---|
| 0x01 | 设置速度 | `p0` = PWM 刻度 0..7200 | `Motion_SetSpeed(p0)`（比赛流程里 6480 ≈ 90%） |
| 0x02 | 切换控制模式 | `p0` = 0 空闲 / 1 角度环 / 2 循迹 / 3 三级串级；`flags.bit0` = 两轮直给 → `p1`=左、`p2`=右 | `Motion_SetMode()`；两轮直给走 `SpeedControl_Enable(1)+SetTarget()` |
| 0x03 | 转到角度 | `p1` = 相对角（度，±）；`p2` = 容差（0.1° 单位，0 → 10 = 1.0°）；`p0` = 超时 ms | 记下进入时航向 → `GyroControl_SetTargetAngle(航向+p1)`，误差收敛或超时后进下一块 |
| 0x04 | 执行舵机动作 | `p0` = 动作号 1..14；`p2` = 动作后等待 ms | `Servo_ApplyAction(p0)`（非阻塞，只走终点姿态） |
| 0x05 | 延时 | `p0` = 毫秒 | 纯等时间 |
| 0x06 | 等待条件 | `p0` = 条件号；`p1` = 阈值；`p2` = 超时 ms；`p3` = 超时后跳到的状态（0xFFFF = 继续） | 条件满足 → 下一块 |
| 0x07 | 跳到状态 | `p0` = 目标状态号 | 立刻切换（重跑目标状态的 enter 块） |
| 0x08 | 结束 | — | 停车、任务结束 |
| 0x09 | 摆舵机 | `p0` = 通道 1/2；`p1` = 角度 0..180 | `Servo_Control()`（手工姿态，调试用） |
| 0x0A | 清横线计数 | — | `tracing_cross_clear()` |

### 3.2 条件（`等待条件` 的 `p0`）

| 编号 | 名字 | 阈值 `p1` | 判据 |
|---|---|---|---|
| 1 | 回到中线 | 0.1 单位（默认 5 = 0.5） | `abs(PID_Tracing_TracePos() - 4.5) <= p1/10` |
| 2 | 丢线 | 灰度阈值（默认 60） | 8 路 `trace_cal_level(i)` 全部 `< p1` |
| 3 | 找回线 | 灰度阈值（默认 60） | 至少一路 `>= p1` |
| 4 | 横线/路口 | — | `tracing_cross() != 0`（满足后自动 `tracing_cross_clear()`） |
| 5 | 横线计数 | 次数 | 解释器累计的横线次数 `>= p1` |
| 6 | 角度到位 | 0.1°（默认 10 = 1.0°） | `abs(GyroControl_HeadingError()) <= p1/10` |
| 7 | 里程 | 编码器计数 | 解释器累计 `sum(abs(SpeedControl_Counts(0..1))) >= p1` |
| 8 | 故障 | — | `Motion_GetFault() != 0` |
| 9 | 立即 | — | 恒真（配合超时 = 纯延时，用于统一写法） |

> 不做的（v1）：变量/表达式、if/else、循环、嵌套子状态机、无线联网判断。
> 需要"计数到 N 才走"这种，用条件 5/7；需要"两条路"就用两个状态 + 跳转。

## 4. 二进制程序格式（v1，小端、紧凑）

```
Header 12 B
  0  u16 magic      = 0x4B54 ('K','T')
  2  u8  ver        = 1
  3  u8  n_states   (1..16)
  4  u8  main_state (主页状态号)
  5  u8  reserved
  6  u16 crc16      (对 header 之后全部字节算，同协议 CRC16)
  8  u16 total_len  (整段程序字节数)
 10  u16 reserved2

状态表 n_states × 8 B（紧接 header）
  0 u16 name_off  (名字在名字区偏移；0 = 无名)
  2 u16 enter_off (enter 块序列偏移；0 = 无)
  4 u16 body_off  (body 块序列偏移)
  6 u8  n_enter
  7 u8  n_body

块 10 B（紧接状态表，按状态分段存放）
  0 u8  op
  1 u8  flags     (bit0 保留：超时算失败 / 两轮直给)
  2 u16 p0
  4 i16 p1
  6 u16 p2
  8 u16 p3

名字区：UTF-8，**无长度字段、无 NUL 结尾**，name_off = 0 表示无名
```

> ⚠️ **读名字的唯一正确姿势**：单个名字的结尾只能靠"**下一个更大的偏移**"来定界 —— 把所有
> `name_off`/`enter_off`/`body_off`（共 3×n_states 个）连同 `total_len` 一起排序，取比本名字
> `name_off` 大的第一个值（没有就用 `total_len`）当结尾。**不许用 `printf("%s")` 读**：名字区没有
> 终止符，`%s` 会把下一个名字一起咽下去（`web/src/lib/task.ts` 的 `decodeTask()` 里的
> `nameEnd()` 就是这么写的；`tools/console/tests/c/taskcheck.c` 里留了一个反例注释）。
> 代价是固件将来要在 `T_TASK_LIST_R` 里回 `u8 name_len` 时也得自己算这个长度；如果嫌烦，
> v2 最省事的改法是每个名字后面补一个 `'\0'`（每个具名状态多 1 字节）。

- 定长块是刻意的：解释器不需要变长解码，手机上（未来）也好生成。
- **容量**：目录最多 8 个任务（页 59 = 8 条 40B 记录），程序区 6KB（页 60..62 =
  `0x0801E000..0x0801F7FF`），单个任务上限 = 解释器 RAM 上限 2048B；
  典型 8 状态 × 12 块 ≈ 1.1KB ⇒ 程序区实际装得下 5 个左右。
- **页分配的唯一权威是 `firmware/App/Svc/task_store.h` 头部注释**（改了那边要同步改
  `firmware/STM32G474RBTx_FLASH.ld` 和这里）：
  页 59 = `0x0801D800` 目录页、页 60..62 = `0x0801E000..0x0801F7FF` 程序区、页 63 =
  `0x0801F800` nvram（任务模块绝不碰）。链接脚本 FLASH 从 126K 收到 **118K**
  （= 页 59 起点；`tools/flash.ps1` 默认按镜像范围擦，不动这几页；`-MassErase` 才会清掉任务）。
- 存储语义：写一个任务 = **先擦目录页**再擦/写程序区（掉电中断宁可看到"没有任务"，
  也好过"半个新程序配旧偏移"——跑错轨迹比不跑更糟）。**运动中拒绝写入**（`ST_BUSY`），
  与 nvram 同一规矩；分片上传只写 RAM 暂存（`TaskStore_Stage`），车在动也允许。
- ⚠️ 尺寸余量（2026-10-03 实测）：收到 118K 后镜像**差 8 字节链不进去**
  （`.data` LMA 末 = `0x0801D808`，需要 120840B，区域只有 120832B）⇒ 见 §8 末的待办。

## 5. 链路协议（新增帧）

**已实现**（`firmware/App/Svc/host_link.c` 的任务段，0x60..0x69；主机测试
`firmware/test/t_hostlink.c` 第 24..32 节 272 项检查）。id 就是**槽号 0..`TASK_STORE_SLOTS`-1`**
（`task_store.h` 没有单独的 id 读取口 ⇒ 帧里的 id 一律 = 槽号）。

| 帧 | 方向 | 载荷 | 实现口径 |
|---|---|---|---|
| `T_TASK_LIST = 0x60` | →车 | — | 只挂"待发"标记，实际回包由 `host_link_poll` 一帧帧发 |
| `T_TASK_LIST_R = 0x61` | 车→ | 一条任务一帧：`u16 id, u16 len, u16 crc, u8 flags, u8 name_len, name…`；**目录发完再发一帧空载荷（len = 0）收尾** | 空槽跳过不发；`name_len` 由 `TaskStore_Name()` 给（最多 30，名字里不带 `'\0'`） |
| `T_TASK_PUT = 0x62` | →车 | `u16 id + u16 off + 数据`（帧载荷上限 128 ⇒ 数据 ≤ 120） | 只写 RAM 暂存（`TaskStore_Stage`），**车在动也允许**；`id` 越界或 `off+本片` 越过 2048 回 `ST_OUT_OF_RANGE`，否则 `ST_OK` |
| `T_TASK_COMMIT = 0x63` | →车 | `u16 id + u16 len + u16 crc`（可选超集：再跟 `u8 name_len + name`，即 `len>6` 时 `p[6]`=name_len、`p[7..]`=名字） | `renwu_flag != 0` ⇒ `ST_BUSY`；`TaskStore_Commit(...)` 校验 CRC+格式后擦写；`ST_OK` / `E_BUSY`→`ST_BUSY` / 其余→`ST_BAD_PARAM`。**flags 目前只能给 0**：`TASK_STORE_FLAG_AUTO`（开机自启）还没有下发通路，要用得给 COMMIT 加一个 flags 字节（桥和固件一起改） |
| `T_TASK_GET = 0x64` | →车 | `u16 id` | 空槽 ⇒ `ST_NOT_READY`；**成功时故意不回 ACK**，改成连续 `T_TASK_DATA`（这就是应答） |
| `T_TASK_DATA = 0x65` | 车→ | `u16 id, u16 off, 数据`，每帧 **64 B** 数据 | **收尾 = 一帧不带数据的 DATA（载荷只有 4 字节 id+off）**。桥按此判断读完 |
| `T_TASK_DEL = 0x66` | →车 | `u16 id` | `renwu_flag != 0` ⇒ `ST_BUSY`；否则 `TaskStore_Erase(slot)` |
| `T_TASK_RUN = 0x67` | →车 | `u16 id` | `renwu_flag != 0` ⇒ `ST_BUSY`；**正在被上位机驾驶**（`HostExt_DriveEnabled()`）⇒ `ST_BUSY` + 文本 `[fw] task run refused: host driving`；`TaskStore_Load()` 失败：`E_EMPTY`→`ST_NOT_READY`、`E_BUSY`→`ST_BUSY`、其余→`ST_BAD_PARAM`；成功再 `TaskRun_Start(id)` |
| `T_TASK_STOP = 0x68` | →车 | — | `TaskRun_Stop()`（幂等，且会停车）+ `ST_OK` |
| `T_TASK_STATUS = 0x69` | 车→ | `u16 id, u8 state, u8 running, u16 block, u32 elapsed_ms, u8 flags`（**11 字节**） | 内容一变就推 + 没变时 1Hz 心跳；未载入任何程序时 `id = 0xFFFF`、`state = TASK_RUN_OFF(0xFF)`、`running = 0` |

两个实现约束（改动前先读 `firmware/App/Svc/host_link.c` 的注释）：

- **每拍最多回一帧**（`TASK_TX_PER_POLL 1`）：`board_dl_send()` 是**同步阻塞**的，一帧
  64B+12B 头在 115200 下 ≈6.5ms ≈ 一帧 `T_TELEM2` 的量级。若在 `handle_frame` 里连发，
  一次 2048B 读回（33 帧）会把主循环按住 200ms 以上：遥测断、OLED 不刷，驾驶时还可能被
  500ms 看门狗误判成掉线。参数全表 dump 早就因此改成同一套路（`s_dump_busy`）。
- **收尾帧是必需的**：§2 的语法允许 `n = 0`，而帧里没有"还有更多"标志位，所以用一个
  空载荷（LIST_R）／不带数据的 DATA 当无歧义的结束标志；桥必须按这个约定收尾，
  不能靠"超时没新帧了"来判断。

`T_HELLO` 的能力位加 **bit7 `HOST_CAP_TASK`**（老固件不置位 ⇒ 上位机把「任务」页禁用并提示）。

实现时对 §2/§4 细化三处（**以代码为准**）：

1. **末尾块规则只约束 body**：`enter` 序列是「进门做一次」的准备工作，末尾是普通块完全正常
   （跑完自动接 body）；**body** 末尾必须是 `跳到状态`/`结束`/带超时跳转的 `等待条件`，
   否则 `TASK_E_TAIL`。
2. **`flags.bit0 = 有过超时`**：`等待条件`、`转到角度` 只要因超时放行就置位（**包括超时改道**
   那条分支）；**`flags.bit1 = 已正常结束`**（跑到过 `结束` 块）。两位都随遥测回传。
3. **未使用字段的填充值不作规定**：解释器只读它用得到的字段（例如 `设置速度` 不读 `p1/p2/p3`），
   上位机填 0 或 0xFF 都行。
