# 任务编程（上位机可编程状态机）设计

> 目标（用户原话，m17516）：**"任务车只是一个执行机构，具体流程都是上位机搞的"** ——
> 上位机拼任务 → 存成二进制程序 → 烧进车的 Flash → 车离线自主执行。
> 多个任务、每个任务多个状态模块、每个状态模块内部用基础块拼；主页负责常态循迹与状态切换。

## 0. 三个待用户确认的决策（本文档按此定案，用户可否决）

| 决策 | 取的值 | 备选 |
|---|---|---|
| 执行位置 | **程序存车上 Flash、车离线自主跑**（比赛不能遥控；上位机只负责编辑/烧写/监视当前状态与块号） | 上位机在线逐条解释下发（实现快，但比赛时必须有上位机连着） |
| 基础块 v1 | **8 类块 + 9 类条件**（见 §3），不含变量/分支/循环 | 加变量、if/else、块内循环（表达力强，代码量与出错面大一圈） |
| （后续追加，格式没动） | 块 `0x0B` 切标定套（2026-10-07）；条件 `10` 指定哪几路是黑的、条件 `11` 指定哪几路是白的、「等条件」的"满足后跳转"（2026-10-07，占 `flags` 的空位）；「等条件」的**"需持续 N×100ms"**（2026-10-07，占 `flags` 低 7 位的**另一档**：`bit7`=0 时才是需持续，=1 时仍是跳转目标）—— 见 §3.1/§3.2/§3.3 的 ★ 行 | 换块号 / 升版本号（老镜像与老任务文件会全部作废） |
| 状态内部结构 | **状态 = 顺序块序列 + 可选"进入块"**；主页 = 常态循迹状态；收尾用「跳到状态」或「结束」 | 状态内再套一层子状态机（界面多两层） |

## 1. 数据模型（上位机视角）

```
Task          任务：名字 + 若干状态 + 指定哪个是主页
  └ State     状态模块：名字 + enter 块序列（进入时跑一次）+ body 块序列
      └ Block 基础块（叶子）：一个动作 / 一个等待
```

- **主页（main）**：任务的入口状态，通常就是"常态循迹"。任务启动后从主页面开始跑。
- 其它状态是"插进来的模块"（过障碍、爬坡、倒库…）。任何状态都能用 `跳到状态` 切走，
  干完活再 `跳到状态(主页)` 回到常态循迹。
- 一个车辆可存**多个任务**；任选一个启动。

### 1.1 ★推荐结构：「主页分派」（2026-10-09，用户定案）

旧内置流程 `renwu.c` 的真身是「**一个主循环一直循迹 + 一串 `if (8路全黑 && black_num==N)`**」。
要写成同构的任务，用 `0x0D 如果…就跳` + `0x0C 记段号`：

```
状态 0（主页）   enter: 切换模式 = 循迹           ← 一直循迹（= 旧代码开头那句 motor_tracing_pid(4.5)）
                body : [如果 8路全压黑 → 状态1]      ← 第 1 条 = 第 1 次压线（序号不用填）
                       [如果 第1~5路压黑 → 状态2]    ← 第 2 条 = 第 2 次压线
                       …（一条判断对应一段）
                       [跳到状态 0]               ← 一条都没中：继续循迹、下一拍接着判断
状态 k+1（第 k 段）body: 那一段的动作…
                       [跳到状态 0]               ← 干完出来，回主页接着分派
                                                  （最后一段收在「结束任务」）
```

- **为什么必须用 0x0D 而不是 0x06**：0x06「等条件」会**停在那里等**它成立 ——
  写在主页上，第一条就把执行流卡住了，第二条永远轮不到。那是"轮流等"，不是"分派"。
- ★**序号不用填**（2026-10-10 用户定案）：主页循环体里**第 k 个「如果…就跳」= 第 k+1 次压线**，
  解释器自己数（`s_dispatch_n` 每成功分派一次 +1，与该块在当前序列里的下标 `s_idx` 比对）。
  ⇒ 用户只填两样：**哪几路压黑**、**跳到哪个状态**；段尾也**不需要**「记段号」。
  （旧代码 `black_num==N` 那一半就是"这是第几条判断"，只是以前要手填、现在自动。）
- **顺序分派**：前一条没成功，后一条**不许抢先**（`s_idx != s_dispatch_n` 就直接往下走）。
  所以"某一段没触发"时，车会一直停在主页循迹 —— 这正是旧代码的行为，也是"必须完成"的要求。
- 每条判断的 `p1` 掩码就是旧代码那一路的 `tracing_data[...]==0`（哪几路压黑），
  与条件 10 是**同一份判据**（都用 `ch_black()`），不会出现两套口径。
- 参考产物：`tools/console/web/src/lib/tasks/renwu-lap.json`（**22 状态 / 219 块 / 2479 B**，
  主页 21 条判断 + 21 个段状态），生成器 `out/_gen_lap5.py`。

## 2. 执行语义（固件侧解释器）

- 5ms 一拍、**全非阻塞**（旧 `renwu.c` 有 210 处 `HAL_Delay()`，新系统一个都不用）。
- 进入状态：先顺序跑 `enter` 块（跑完），再顺序跑 `body` 块；`body` 跑到底没有跳转 = 状态停住
  （最后一块必须是「跳到状态」或「结束」，上位机编辑器会校验这一点）。
- 块分两类：**立即块**（执行完立刻进下一块）与**等待块**（每拍查条件，满足/超时才进下一块）。
- 任何时刻只有一个状态在跑；`跳到状态` = 立刻切换（不等待），进入新状态重跑它的 enter 块。
- 任务结束（`结束` 块）或出错停机：`Motion_Stop()` + `SpeedControl_Stop()`。
- 遥测回传：`当前任务号 / 状态号 / 块号 / 该块已运行 ms / 超时标志`（上位机据此高亮正在跑的那一块）。
- **安全**：程序运行期间**不**受上位机链路看门狗约束（比赛要离线自主）；`T_CMD_STOP`、
  `T_TASK_STOP`、急停仍然随时能停。

## 3. 基础块与条件（v1）

### 3.1 块（10 字节定长，见 §4）

| op | 名字 | 参数 | 语义 |
|---|---|---|---|
| 0x01 | 设置速度 | `p0` = PWM 刻度 0..7200 | `Motion_SetSpeed(p0)`（比赛流程里 6480 ≈ 90%） |
| 0x02 | 切换控制模式 | `p0` = 0 停车 / 1 角度环 / 2 循迹环+速度环 / 3 循迹（三层串级）；`flags.bit0` = 两轮直给 → `p1`=左、`p2`=右 | `Motion_SetMode()`；两轮直给走 `SpeedControl_Enable(1)+SetTarget()`。**上位机下拉只暴露 0/1/3 三项**（0 停车 / 1 角度环 / 3 循迹）—— 2 与两轮直给是旧形态，格式与固件仍然支持、老镜像仍然跑得动，只是不再提供（用户 m19122 定案） |
| 0x03 | 转到角度 | `p1` = 相对角（度，±）；`p2` = 容差（0.1° 单位，0 → 10 = 1.0°）；`p0` = 超时 ms | 记下进入时航向 → `GyroControl_SetTargetAngle(航向+p1)`，误差收敛或超时后进下一块 |
| 0x04 | 执行舵机动作 | `p0` = 动作号 1..20；`p2` = 动作后等待 ms | `Servo_ApplyAction(p0)`（非阻塞，只走终点姿态） |
| 0x05 | 延时 | `p0` = 毫秒 | 纯等时间 |
| 0x06 | 等待条件 | `p0` = 条件号；`p1` = 阈值（条件 10/11 时是 8 位掩码）；`p2` = 超时 ms；`p3` = 超时后跳到的状态（0xFFFF = 继续）；`flags` 一个字节装两件事、**按 bit7 分档**（见 §3.3）：bit7 = 1 ⇒ 低 7 位 = 满足后跳到的状态号；bit7 = 0 ⇒ 低 7 位 = **需持续的 100ms 格数**（0..127 ⇒ 0..12.7s，**0 = 不要求持续**） | **满足** → 接着执行下一块，或（`flags.bit7` = 1）跳到那个状态；**超时** → 跳 `p3`。带"需持续"时，"满足"= 条件**连续**成立够那么多格（**断一次就重新计时**）。两条出路互不影响，见 §3.3 |
| 0x07 | 跳到状态 | `p0` = 目标状态号 | 立刻切换（重跑目标状态的 enter 块） |
| 0x08 | 结束 | — | 停车、任务结束 |
| 0x09 | 摆舵机 | `p0` = 通道 1/2；`p1` = 角度 0..180 | `Servo_Control()`（手工姿态，调试用） |
| 0x0A | 清横线计数 | — | `tracing_cross_clear()` |
| 0x0B | 切换灰度标定套 | `p0` = 0 普通 / 1 亚克力 | `trace_cal_select_set(p0)`（2026-10-07 补：在这块之前，跑任务时没有任何办法切换那两套标定） |
| 0x0C | **记段号** | `p0` = 段号（0..255） | `s_stage = p0` —— 旧代码的 `black_num = M`。任务启动时段号清 0（`TaskRun_Start()`） |
| 0x0D | **如果…就跳** | `p1` = 8 位掩码；`p2` = 目标状态；**`p0` = 满足时间（毫秒，0 = 不滤波）** | **看一眼就走**：掩码那几路压黑**且连续成立 ≥ `p0` 毫秒** ⇒ 跳到 `p2`；否则**执行下一块**（中途断一次就重新计时）。★**序号不用填**：主页循环体里**第 k 个本块 = 第 k+1 次压线**，固件自己数（2026-10-10 用户定案：手填的段号那一格删掉）。★**`p0` 的用途（2026-10-10 用户："加上滤波，就是满足时间，默认 100ms"）**：探头排横着装 ⇒ **十字路口的横向黑线与探头排平行、8 路也会同时压黑**，与"骑上障碍的黑砂面"是同一个信号；路口那一下很短（3.8cm 线 @0.5m/s ≈ 76ms），障碍前的黑带面积大得多 ⇒ 要求持续 100ms 就能把路口滤掉。**`p0 = 0` = 不滤波，与加这个功能之前逐字节等价**（老镜像/老任务 `p0` 全是 0，固件以前也不读它）。计时用毫秒（`s_now`）而非"被执行了几次"—— GOTO 自环让一拍里 body 会被走好几遍。★与 0x06「等条件」的根本区别：0x06 会**停在那里等**它成立，本块不满足就往下走 —— 主页能并排写 N 条判断全靠它。掩码 0 或目标越界都当"不成立"（绝不越界跳） |
| 0x0E | **爬台阶（循环到车平）** | `p0` = 要爬几节；`p1` = 抬起阈值(0.1°)；`p2` = 回落容差(0.1°)；`p3` = 没满足时跳回的状态 | 把这一段动作一遍遍重复：**跑够 `p0` 节 且 车头真的落回水平**才往下走；否则跳到 `p3`（一般填**本状态自己**）。基准俯仰角 = **进这个状态那一刻**的角度（会话在 `seq_begin()` 里开，所以"跳回自己"不会把它重置）；一次会话按**段号**区分 ⇒ 同一个块放在大坡和台阶3 两处不会串。★`p1` 是防"打滑滑下来"的：滑下来同样是"先抬头再落回"，要求先真的抬过 `p1` 那么高，那次回落才算数（填 0 = 不要求）。★**没有超时**，不满足就一直重试 —— 要收手就在它后面接「停车」或「结束任务」 |

### 3.2 条件（`等待条件` 的 `p0`）

| 编号 | 名字 | 阈值 `p1` | 判据 |
|---|---|---|---|
| 1 | 回到中线 | 0.1 单位（默认 5 = 0.5） | `abs(PID_Tracing_TracePos() - 4.5) <= p1/10` |
| 2 | 丢线 | 灰度阈值（默认 60） | 8 路 `trace_cal_level(i)` 全部 `< p1` |
| 3 | 找回线 | 灰度阈值（默认 60） | 至少一路 `>= p1` |
| 4 | 横线/路口 | — | `tracing_cross() != 0`（满足后自动 `tracing_cross_clear()`） |
| 5 | 横线计数 | 次数 | 解释器累计的横线次数 `>= p1` |
| 6 | 角度到位 | 0.1°（默认 10 = 1.0°） | `abs(GyroControl_HeadingError()) <= p1/10` |
| 7 | 里程 | 编码器计数 | 解释器累计 `sum(abs(SpeedControl_Counts(0..1))) >= p1` |
| 8 | 故障 | — | `Motion_GetFault() != 0` |
| 9 | 立即 | — | 恒真（配合超时 = 纯延时，用于统一写法） |
| **10** | **指定哪几路是黑的**（★2026-10-07） | **8 位掩码**（bit0..bit7 = 第 1..8 路） | 勾中的那几路**当前全是黑的**；其余通道一律不管。**掩码 = 0 ⇒ 恒不满足** |
| **11** | **指定哪几路是白的**（★2026-10-07） | **8 位掩码**（同上） | 上面那条的**镜像**：勾中的那几路**当前一路都不黑**（全白）；其余通道一律不管。**掩码 = 0 ⇒ 恒不满足** |

#### 条件 10 / 11 的口径（★2026-10-07 用户 m 要求）

- **掩码**：`p1` 的低 8 位，bit0 = 第 1 路 … bit7 = 第 8 路。上位机把它画成 **8 个多选框**（条件下拉选中这两条中的任意一条时才出现，占的是原来"阈值"那一格；标题跟着条件改口成「哪几路是黑的」/「哪几路是白的」）。
- **判据（语义 A）**：**勾中的那几路必须同时满足**（10 = 全黑 / 11 = 全不黑），没勾的是黑是白都不管。想要"某几路黑 **且** 其余全白"这种更严的判据，现在做不到（一个块只有 `p0..p3` 四个位，掩码已占满；真要就得另开一个块号拆成"必须黑/必须白"两组）。所以它们能表达"左半边压线""中间两路压线""右三路已经出线"这类形状，**不能**表达"精确居中"。
- **掩码 = 0**（一路都没勾）：**两条都是恒不满足 —— 黑白两个条件在这个口径上完全一致**。这是显式定的语义：0 路的"全黑/全白"都是空真，若按空真处理这个条件会**立刻通过**（等于一块什么都不等的块，会让状态机瞬间被推过去），那是陷阱不是本意。界面上这种情况下会当场提醒"这个条件永远不会满足"。
- **逐路取"黑"**：`trace_cal_channel(i)`（1 = 压黑线 / 0 = 没压）。它可能回 **-1**（没标定 / 这一路标定无效 / 用户把「灰度接口」定死成数字口、要调用者回落），这时退回同一份柱高的半高判定（= 界面那个 0/1 的口径，数字口模式下就是 0/255 真值）；**仍然判不出来就当"没压黑"** —— 两个条件共用这一个判断（`task_run.c` 的 `ch_black()`），所以同一份灰度数据永远不会出现"一路既算黑又算白"。注意这个保守方向对两条条件是相反的：判不出来时条件 10 **不满足**（卡在等待里，有超时兜底），条件 11 **满足**。灰度坏到连柱高都读不出时，两条都可能不如预期 —— 那是标定问题，不是条件本身的问题。
- 固件里它们是 `TASK_C_CH_BLACK = 10` / `TASK_C_CH_WHITE = 11`，实现见 `firmware/App/Svc/task_run.c` 的 `cond_ok()`。

### 3.3 「等条件」的三件事：需持续 / 满足后 / 超时后（★2026-10-07）

一个「等条件」块有**三条独立的出路/条件**，`p0..p3` 已被"条件 / 阈值 / 超时 / 超时后"占满，
第 5、第 6 个参数只能用那个 `flags` 字节 —— 而它只有 8 位，所以**按 `bit7` 分成两档**：

| | 存哪 | 语义 |
|---|---|---|
| **需持续**（★新） | `flags` 低 7 位，**只在 `bit7` = 0 时** | 低 7 位 = 需要**连续**成立的 100ms 格数（0..127 ⇒ 0..12.7 s）。**0 = 不要求持续**（= 老行为）。含义：这段时间内条件必须**一直成立**；**中途断一次，计时清零、重新从零累计**（不是"累计够 1 秒"、也不是"曾经成立过就行"） |
| **满足后** | `flags.bit7`（1）+ 低 7 位（目标状态号） | bit7 = 1 ⇒ **立刻跳到那个状态**；bit7 = 0 ⇒ **接着往下走一块**（默认）。⚠ 这一档用掉了低 7 位 ⇒ **与"需持续"互斥**，同一块只能有一个 |
| **超时后** | `p3`（0xFFFF = 继续往下） | 等够 `p2` 毫秒还没满足 ⇒ 跳 `p3`（0xFFFF = 接着往下走一块），同时置 `TASK_RUN_F_TIMEOUT`。**超时从"进入这一块"算起**，与"需持续"的计时互不影响 |

- **语义要点（"需持续"）**：条件首次成立的那一拍记起点（那一拍算已持续 0 ms），此后每 5 ms 一拍
  检查 `now - 起点 >= 需持续`。**关键是"连续"**：只要有一拍不成立，这一轮就作废，下次成立时
  重新取起点。典型用法 = 「扫到两段超过 1 s 的全黑」这种**必须压在障碍上足够久**的判据。
  实现见 `firmware/App/Svc/task_run.c` 的 `case TASK_OP_WAIT_COND`（`s_hold_run` / `s_hold_from`）
  —— **全非阻塞**，一个 `HAL_Delay` 都没有；换块时计时清零（`TaskRun_Tick()` 的 `if (!s_started)`）。
- **两者都要怎么办**："持续够久再跳走"**不要**写 `bit7`，写成「等条件(需持续) + 紧跟一块 `0x07 跳到状态`」
  —— 等待块满足后立刻执行下一块，那块 GOTO 立刻跳，**执行流与"满足后跳转"完全等价**。
  固件里 `flags.bit7` = 1 时低 7 位一律当跳转目标读、**不再当"需持续"**（否则跳转目标就废了）。
- **为什么不换块号**：块是 **10 字节定长**（op + flags + p0..p3），第 5 个参数只能用 `flags` 字节。
  这样**任务文件格式与版本号一个字节都不用动**，老文件照样解析。
- **向后兼容（已核，这是硬证据不是推断）**：老任务（`renwu-lap.json`、`quancheng-v3.json` 改前那版、
  以及车上所有既有镜像）的「等条件」块 `flags` **全是 0** ⇒ `bit7` = 0 且低 7 位 = 0 ⇒
  "需持续 = 0" ⇒ **满足即通过，与加这个功能之前逐字节、逐拍等价**。
  `flags.bit0` 是**另一个 op**（`0x02` 两轮直给、`0x03` 相对角度）用的，与这里不冲突。
- 上位机：「等条件」多了一栏**「满足后」**，下拉里是「继续往下跑」（默认）+ 每个状态；写文件时翻译成
  `flags` 的 bit7+低 7 位（`lib/task.ts` 的 `waitCondJumpTarget()` / `withWaitCondJumpTarget()`），
  界面/摘要里再翻译回状态名。**「需持续」**由 `lib/taskedit.ts` 的 `waitCondHoldMs()` /
  `withWaitCondHoldMs()` 负责（单位 ms、**按 100 ms 量化**、范围 0..12700），并显示在块摘要里
  （「…需持续 1000ms（这期间必须一直成立，断一次就重新计时）」）。⚠ 它的**输入框**要动
  `pages/Tasks.tsx` 的字段渲染（`flags` 那一格现在被专门路由给"满足后"下拉），
  在补上之前，改这个值要**手改 JSON**：那三块写 `"flags": 10` 就是"需持续 1000ms"（10 格 × 100ms）。
- ⚠ **末尾块的限制**：固件的格式校验 `tail_ok()`（`task_prog.c`）**只认 `p3`**（跳到状态 / 结束 /
  带超时跳转的等待）—— 它不看 `flags`。所以一个"满足后跳走、超时那栏却留着继续往下"的「等条件」
  **放在循环体最后一块会被固件拒收**（`TASK_E_TAIL`）。上位机校验保持同一口径（`isTailBlock()`
  也只看 `p3`），并额外给一句更具体的提示。要在末尾用它，就给"超时后"配一个真状态。
- 目标状态越界（程序后来被改过、状态被删了）：固件**当"继续往下"处理**，绝不越界跳；上位机校验会报错。

> 不做的（v1）：变量/表达式、if/else、循环、嵌套子状态机、无线联网判断。
> 需要"计数到 N 才走"这种，用条件 5/7；需要"两条路"就用两个状态 + 跳转。

## 4. 二进制程序格式（v1，小端、紧凑）

```
Header 12 B
  0  u16 magic      = 0x4B54 ('K','T')
  2  u8  ver        = 1
  3  u8  n_states   (1..16)
  4  u8  main_state (主页状态号)
  5  u8  reserved
  6  u16 crc16      (对 header 之后全部字节算，同协议 CRC16)
  8  u16 total_len  (整段程序字节数)
 10  u16 reserved2

状态表 n_states × 8 B（紧接 header）
  0 u16 name_off  (名字在名字区偏移；0 = 无名)
  2 u16 enter_off (enter 块序列偏移；0 = 无)
  4 u16 body_off  (body 块序列偏移)
  6 u8  n_enter
  7 u8  n_body

块 10 B（紧接状态表，按状态分段存放）
  0 u8  op
  1 u8  flags     按 op 解释：0x02/0x03 用 bit0（两轮直给 / 相对角度）；
                   0x06「等条件」**按 bit7 分档**（低 7 位只有一个）：
                     bit7 = 1 ⇒ 低 7 位 = 满足后跳到的状态号（0 = 满足后继续往下）
                     bit7 = 0 ⇒ 低 7 位 = 需持续的 100ms 格数（0 = 不要求持续）
                   见 §3.3
  2 u16 p0
  4 i16 p1
  6 u16 p2
  8 u16 p3

名字区：UTF-8，**无长度字段、无 NUL 结尾**，name_off = 0 表示无名
```

> ⚠️ **读名字的唯一正确姿势**：单个名字的结尾只能靠"**下一个更大的偏移**"来定界 —— 把所有
> `name_off`/`enter_off`/`body_off`（共 3×n_states 个）连同 `total_len` 一起排序，取比本名字
> `name_off` 大的第一个值（没有就用 `total_len`）当结尾。**不许用 `printf("%s")` 读**：名字区没有
> 终止符，`%s` 会把下一个名字一起咽下去（`web/src/lib/task.ts` 的 `decodeTask()` 里的
> `nameEnd()` 就是这么写的；`tools/console/tests/c/taskcheck.c` 里留了一个反例注释）。
> 代价是固件将来要在 `T_TASK_LIST_R` 里回 `u8 name_len` 时也得自己算这个长度；如果嫌烦，
> v2 最省事的改法是每个名字后面补一个 `'\0'`（每个具名状态多 1 字节）。

- 定长块是刻意的：解释器不需要变长解码，手机上（未来）也好生成。
- **容量**：目录最多 8 个任务（页 58 = 8 条 40B 记录），程序区 6KB（页 59..61 =
  `0x0801D800..0x0801EFFF`），单个任务上限 = 解释器 RAM 上限 **4096B**
  （`TASK_STORE_CAP` / `TASK_RUN_MAX_PROG`）；
  典型 8 状态 × 12 块 ≈ 1.1KB ⇒ 程序区实际装得下 5 个左右。
  2026-10-03 由 2048 提到 4096：旧内置比赛流程（`renwu.c` 的 12 个障碍）转成任务块要 **2127B**
  （190 块 / 15 状态 / 名字 95B），2048 装不下；**字节格式没变**（还是 v1、10B 一块），
  变的只是允许的长度上限，老镜像照跑。
- **页分配的唯一权威是 `firmware/App/Svc/task_store.h` 头部注释**（改了那边要同步改
  `firmware/STM32G474RBTx_FLASH.ld` 和这里）：
  页 58 = `0x0801D000` 目录页、页 59..61 = `0x0801D800..0x0801EFFF` 程序区、页 62 =
  `0x0801F000` 空着（它和页 63 同属 nvram 的擦除块 31，nvram 每存一次参数会连带擦掉它）、
  页 63 = `0x0801F800` nvram（任务模块绝不碰）。链接脚本 FLASH 从 126K/118K 收到 **116K**
  （= 页 58 起点；`tools/flash.ps1` 默认按镜像范围擦，不动这几页；`-MassErase` 才会清掉任务）。
  ⚠️ **本板的擦除粒度是 4KB 块**（块号 = 页号/2，块地址 = `0x08000000` + 块号×4096，
  BKER 被硬件忽略；2026-10-04 真板实测）——早先"页 59 目录 + 页 60..62 程序区"的布局
  在块模型下会擦到块 27/28/31，其中块 27/28 就是固件镜像自己（真机上表现为"一提交任务 App
  立刻 HardFault"）。新布局只占块 29/30。
- 存储语义：写一个任务 = **先擦目录页**再擦/写程序区（掉电中断宁可看到"没有任务"，
  也好过"半个新程序配旧偏移"——跑错轨迹比不跑更糟）。**运动中拒绝写入**（`ST_BUSY`），
  与 nvram 同一规矩；分片上传只写 RAM 暂存（`TaskStore_Stage`），车在动也允许。
- 尺寸余量（2026-10-04 修掉两个真机 bug 后，默认 `-Og`）：text 115840 + data 364 ⇒
  `build-app/haixin-app.bin` **116212B**，离 116K（118784B）余 **2572B**。
  （提速前是 114604B / 余 6228B；那次 +1480B = LPUART1 收 DMA 的 2048B 缓冲 + 发 DMA 的
  8×144B 槽位表进 `.bss`、以及 host_link 的每拍 8 帧与 100Hz 默认值，text 本身只涨了约 1.4KB。）
  更早那条「+16 B 来自 `CMD_START_A/B/C` → `ST_UNSUPPORTED` 分支的提示文本」仍然成立：
  **删 `renwu.c` 并没省下尺寸**（旧流程的函数早就没人调用，`-ffunction-sections --gc-sections` 早把它整段丢出镜像）—— 删掉的是 989 行源码与一份维护负担，不是 flash。
  同一天 14:41 曾一度"差 8 字节链不进去"，但那是**树里混着旧 `.o`** 造成的假象
  （经过见 §8.2 待办 1）——**量余量前先整份重建**，混着旧目标文件量出来的是假的。

## 5. 链路协议（新增帧）

**已实现**（`firmware/App/Svc/host_link.c` 的任务段，0x60..0x69；主机测试
`firmware/test/t_hostlink.c` 第 24..32 节 292 项检查）。id 就是**槽号 0..`TASK_STORE_SLOTS`-1`**
（`task_store.h` 没有单独的 id 读取口 ⇒ 帧里的 id 一律 = 槽号）。

| 帧 | 方向 | 载荷 | 实现口径 |
|---|---|---|---|
| `T_TASK_LIST = 0x60` | →车 | — | 只挂"待发"标记，实际回包由 `host_link_poll` 一帧帧发 |
| `T_TASK_LIST_R = 0x61` | 车→ | 一条任务一帧：`u16 id, u16 len, u16 crc, u8 flags, u8 name_len, name…`；**目录发完再发一帧空载荷（len = 0）收尾** | 空槽跳过不发；`name_len` 由 `TaskStore_Name()` 给（最多 30，名字里不带 `'\0'`） |
| `T_TASK_PUT = 0x62` | →车 | `u16 id + u16 off + 数据`（帧载荷上限 128 ⇒ 数据 **≤ 124**；页面按 120 一片分） | 只写 RAM 暂存（`TaskStore_Stage`），**车在动也允许**；`id` 越界或 `off+本片` 越过 `TASK_STORE_CAP`（4096）回 `ST_OUT_OF_RANGE`，否则 `ST_OK` |
| `T_TASK_COMMIT = 0x63` | →车 | `u16 id + u16 len + u16 crc + u8 flags`（可选超集：再跟 `u8 name_len + name`，即 `len>7` 时 `p[7]`=name_len、`p[8..]`=名字；`len==6` 只认前三者、`len==7` 只带 flags） | `flags` 是**保留位**：车上原样存进目录页、不解释任何位（bit0 曾经是「开机自启」`TASK_STORE_FLAG_AUTO`，2026-10-04 用户要求**整个删掉** —— 上电只扫描不启动；启动只有车上任务页中键与 `0x67 RUN` 两条路）；`TaskRun_IsRunning() != 0` ⇒ `ST_BUSY`；`TaskStore_Commit(...)` 校验 CRC+格式后擦写；`ST_OK` / `E_BUSY`→`ST_BUSY` / 其余→`ST_BAD_PARAM`（名字长度撒谎也一样拒） |
| `T_TASK_GET = 0x64` | →车 | `u16 id` | 空槽 ⇒ `ST_NOT_READY`；**成功时故意不回 ACK**，改成连续 `T_TASK_DATA`（这就是应答） |
| `T_TASK_DATA = 0x65` | 车→ | `u16 id, u16 off, 数据`，每帧 **64 B** 数据 | **收尾 = 一帧不带数据的 DATA（载荷只有 4 字节 id+off）**。桥按此判断读完 |
| `T_TASK_DEL = 0x66` | →车 | `u16 id` | `TaskRun_IsRunning() != 0` ⇒ `ST_BUSY`；否则 `TaskStore_Erase(slot)` |
| `T_TASK_RUN = 0x67` | →车 | `u16 id` | `TaskRun_IsRunning() != 0` ⇒ `ST_BUSY`；**正在被上位机驾驶**（`HostExt_DriveEnabled()`）⇒ `ST_BUSY` + 文本 `[fw] task run refused: host driving`；`TaskStore_Load()` 失败：`E_EMPTY`→`ST_NOT_READY`、`E_BUSY`→`ST_BUSY`、其余→`ST_BAD_PARAM`；成功再 `TaskRun_Start(id)` |
| `T_TASK_STOP = 0x68` | →车 | — | `TaskRun_Stop()`（幂等，且会停车）+ `ST_OK`；`CMD_STOP(0x01)` 也走同一条路 |
| `T_TASK_STATUS = 0x69` | 车→ | `u16 id, u8 state, u8 running, u16 block, u32 elapsed_ms, u8 flags`（**11 字节**） | 内容一变就推 + 没变时 1Hz 心跳；**`elapsed_ms` 不参与判变化**（它每毫秒都在变，算进去就退化成"每拍一帧"，2026-10-04 实测把 230400 的链路灌到 338 帧/s、桥 8 秒丢 1904 帧），进度靠 1Hz 心跳刷新；未载入任何程序时 `id = 0xFFFF`、`state = TASK_RUN_OFF(0xFF)`、`running = 0` |

> **★写车前先备份（2026-10-07）**：`python -m bridge.taskbackup`（workdir `tools/console`）= **只读**
> 走一遍 `GET /api/tasks` + 逐槽 `GET /api/tasks/get`，把目录 + 每条任务的**镜像字节**抄到仓根
> `out/taskbackup/`（`<槽>_<名字>_<CRC>.bin` + `index.json`），并逐条校验「长度 / 头 `crc[6..7]` /
> magic `0x4B54` / 头 `len[8..9]` / 按 `bytes[12:]` 重算的 body CRC」—— 任一条不合就报错、退出码 1。
> 起因：两次**参数填错**的 `commit`（`crc` 写成 8..9、`len` 写成 4..5，正确是 **`crc` 6..7、`len` 8..9**）
> 把车上原有三条任务**从目录里抹掉了** ✗（程序区没坏，丢的是目录条目），只能重烧。

两个实现约束（改动前先读 `firmware/App/Svc/host_link.c` 的注释）：

- **每拍最多回 8 帧**（`TASK_TX_PER_POLL 8`）：`board_dl_send()` 现在是**非阻塞**的（2026-10 提速后
  发走 DMA 槽位队列），但队列只有 `DL_TX_SLOTS = 8` 帧深、满了就丢帧，所以仍旧挂"待发"标记、
  每拍推这么多帧 —— 一次 4096B 读回（65 帧）要分 9 拍推完，主循环一帧都不用等。参数全表 dump
  走同一套路（`s_dump_busy`）。改这俩常数前先看 `firmware/App/Svc/host_link.c` 里的注释。
- **收尾帧是必需的**：§2 的语法允许 `n = 0`，而帧里没有"还有更多"标志位，所以用一个
  空载荷（LIST_R）／不带数据的 DATA 当无歧义的结束标志；桥必须按这个约定收尾，
  不能靠"超时没新帧了"来判断。

`T_HELLO` 的能力位加 **bit7 `HOST_CAP_TASK`**（老固件不置位 ⇒ 上位机把「任务」页禁用并提示）。
