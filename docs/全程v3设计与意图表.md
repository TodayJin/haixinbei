## 1. ★ 极性：旧代码里每处条件的**真正含义**

### 1.1 结论（我的判读，以及为什么它必须由你拍板）

`renwu.c` 每一段的入口都长这样：

```c
if (tracing_data[0]==0 && ... && tracing_data[7]==0 && black_num==4) { ... }
```

**`tracing_data` 只可能是 0 或 1**，因为实装的读法就是逻辑非：

```c
// Haixin/Hardware/tracing.c:7-17
tracing_data[0]=!HAL_GPIO_ReadPin(GPIOA,GPIO_PIN_4);   // :9
... tracing_data[7]=!HAL_GPIO_ReadPin(GPIOE,GPIO_PIN_8); // :16
```

★ **两份 `renwu.c` 里 `tracing_data` 的全部 224 处比较都是 `==0`，没有第二種取值。**
（旧板 `Haixin/Hardware/renwu.c` 与 `git show 53b5fc0:firmware/App/Svc/renwu.c` 各数一遍都是 `==0 × 224`；
对 `==2..9` 的命中 **0 行**。带 `==9` / `!=8` 的那段在 **`Haixin/Hardware/tracing.c:96-150`，是整段注释掉的
`motor_tracing_mv()`**（模拟量版，配 `read_tracing_data_mv()`，而那个函数体 `:18-28` 也整段是注释）。
**"9 = 白"只活在注释代码里，从来不是实装路径。**）

那么 `0` 到底是"压线"还是"没压线"？两边证据对撞：

| 支持 **`0` = 白（没压线）** | 支持 **`0` = 黑（压线）** |
|---|---|
| ① `tracing.c:9-16` 对引脚**取反**；而同一个 `HAL_GPIO_ReadPin` 在新板被解释为 **`1 = 压线`**（`host_link.c:496` `if (bsp_trace_bit(i)==GPIO_PIN_SET) m \|= 1u<<i;   /* 1 = 压线 */`，`tracing.c:7`「0 = 压黑线为高（本模块默认）」、`trace_cal.h:117`「1 = 压黑线」）⇒ 取反后 **0 = 压线** | ① 旧板同文件的 `PID_tracing.c:18-25` 用的是**不取反**的原值：`if (HAL_GPIO_ReadPin(...)==GPIO_PIN_SET) {L1=1; num++;}`，而它的控制律在**所有**极端情况下都自洽（全压线 ⇒ `data=4.5` ⇒ 两轮同速原地停；`TurnLeft(60)` 后真往左；`TurnLeftFixed()` 名字与函数体相反 ⇒ 实际转右）⇒ 原值 **1 = 压线** |
| ② `Haixin/Core/Src/gpio.c:70-92` 把 8 根脚命名成 **`IN1..IN8`**、`GPIO_NOPULL`、直接读模块的数字输出 | ② `docs/控制算法升级方案.md:42` 写「`renwu.c` 里『全 0』事件 = 8 路原始位全 SET（**整排压线**）」——但**同一份文档第 1 节自称"读代码得到的事实"却把 `renwu.c` 的死段列错了**（它写 8/12/14/20/22，实测是 **8/12/14/15/16/20/22**），可信度低 |
| ③ **旧板实测原值**（tracked 文档 `docs/灰度标定与检验.md:96-98`）：车停在线上实测 `289 323 318 **201 241** 316 352 330`，**第 4、5 路最低**（正中间压线），且同文 `:70` 写 `极性 pol = 黑比白原值大` ⇒ **黑 = 原值高**；`!` 把它翻成 **0** | ③ `motor_tracing()`（开关式循迹，`tracing.c:40-95`）按 `1 = 压线` 写，且与它自己的分支注释全部自洽（`[0..1]` 压线 ⇒ 停左轮 = 左转 = 线在左边；`[6..7]` 压线 ⇒ 停右轮 = 右转） |

**两边都站得住，因为这是一处旧代码自身的矛盾：同一块板上 `tracing.c` 取反、`PID_tracing.c` 不取反，
读的是同一批引脚（PA4/PA5/PC4/PC5/PB0/PB1/PE7/PE8 一一对应），两者必然有一个是坏的。**
仅凭静态读码**无法**判定当年哪一份是准的（也就无法判定实装硬件在"压线"时给的是 0 还是 1）。

### 1.2 所以 v3 是怎么处理的

- ★**已定案（2026-10-07）：这一份用的是 `CH_BLACK`（条件 10）** —— 即"勾中的那几路**都是黑的**才算等到"，
  与 `renwu-lap.json` 现在的口径一致。下面这段是当初的推演过程，**保留**（它就是定案的依据）。
- **当时的默认判读**：`==0` = 该路**没压线（白）** ⇒ 用条件 **11 `CH_WHITE`**。理由：① 新板固件的权威注释（三处）说数字口"压线为高"，
  而 `renwu.c` 用的正是取反那份 ⇒ 0 = 压线；② 旧板实测原值证明"黑 = 原值高"，取反后同样是 0 = 压线。
- **备用**：`out/_quancheng-v3-flipped.json` 是**同一份设计、只把条件 10/11 对调**（一个 node 一行脚本事，按上面那份现算）。
  两份的**结构、块数、字节数完全一样**（15 / 213 / 2517 B），只有那 13 个条件的 `p0` 在 10 与 11 之间翻。
- **30 秒定案的办法（不用发车、不用烧录）**：把车摆在黑线上，看循迹页/`/api/cal` 的逐路原值 ——
  **压线的那几路原值明显低于两侧**（`docs/灰度标定与检验.md:96` 那组数就是实测）。压线时原值低 ⇒
  数字口原值 = 0 ⇒ `!` 之后 = 1 ⇒ **`==0` 是"没压线"**，用本文件；反之换 flipped 那份。

### 1.3 逐处条件的含义（旧代码 → v3 的块）

| 旧代码写法 | 真正含义 | v3 用的条件块 |
|---|---|---|
| `data[0..7]==0 && black_num==N`（20 处） | 8 路**都没压线**（车离开线/被顶起来/上坡腾空） | `WAIT_COND` 条件 11 `CH_WHITE`，`p1 = 0xFF` |
| `data[0..4]==0`（段 6、17。`data[5..7]` 被注释） | **只看左 5 路没压线**，右边 3 路不管 | 条件 11 `p1 = 0x1F`（bit0..bit4 = 第 1..5 路） |
| `data[3..7]==0`（段 13、16、20、21。`data[0..2]` 被注释） | **只看右 5 路没压线** | 条件 11 `p1 = 0xF8` |
| `data[0..3]==0`（段 19。`data[4..7]` 被注释） | **只看第 1..4 路没压线** | 条件 11 `p1 = 0x0F` |

> 掩码约定：`p1` 的低 8 位，**bit0 = 第 1 路 … bit7 = 第 8 路**；勾中的那几路"全是白的"才算满足，其余通道一律不管；
> **掩码 = 0 ⇒ 恒不满足**（`docs/任务编程.md` §3.2）。v3 里**没有一个掩码是 0**。

## 3. 两个"旧代码本身的坑"（按当年车实际怎么动，不按作者字面意图）

1. **`renwu.c:844` 的 `Load(0,0)` 是失效的。** 那一行执行时角度环还开着（`L840` 开的），而旧板每 10ms 的中断
   （`Haixin/Core/Src/main.c:287-292` → TIM4 → `GyroControl_Task()`）会用「基准±修正」立刻覆盖它 ⇒ **车根本没停**，
   继续按 900/900 走完那 500ms。v3 在这一处**不插停车块**，而是继续走 500ms。
   （反过来，`L535` 的 `Load(0,0)` 发生在角度环**关掉之后**，那个是**生效的**，v3 那里真的停 200ms。两处不一样，别混。）
2. **`TurnLeftFixed()` / `TurnRightFixed()` 名字和函数体是反的**（旧板 `Haixin/Hardware/gyro_control.c:239-250`、
   新板 `firmware/App/Svc/gyro_control.c:998-1009` 一模一样）⇒「左转固定」实际是**右转 90°**。
   v3 按**实测方向**写：`TurnLeftFixed → TURN_DEG +90`、`TurnRightFixed → TURN_DEG −90`（与旧版一致）。

## 6. 已知的一处**无害**不一致（记下来免得下次又查一遍）

`web/src/lib/task.ts` 的 `decodeTask()` 把块字段 `p2` 一律按 **u16** 读（`getUint16`），
而固件在 `op=0x02` + `flags.bit0`（两轮直给）时是按 **i16 符号扩展**的（`firmware/App/Svc/task_run.c:218`：
`SpeedControl_SetTarget((int)b->p1, (int)(int16_t)b->p2)`）。
⇒ 编码器写进去的 `-3889` 字节是 `0xF0CF`（**正确的两补码，固件读出来就是 −3889**），只有 `decodeTask` 会显示成 `61647`。
**编码、固件、实车行为都没问题，只是回读显示**。v3 里两轮直给带负数的块共 **7 个**（栅栏/洞口/十字A/U形/十字C/大坡/十字D/收尾的倒车）。

## 7. 不确定 / 需要拍板的地方

1. **★极性（§1）—— 已定案（2026-10-07）：这份用 `CH_BLACK`（条件 10）**，即"勾中的那几路**都是黑的**才算等到"，
   `renwu-lap.json` 也已被同一处改动翻成 `CH_BLACK`（CRC `0xE021`），两边口径一致。
   判据见 §1.2 最后一条（压线的那几路原值明显低于两侧 ⇒ 数字口取反后 = 压线）。
   若哪天实测反了，用 `out/_quancheng-v3-flipped.json`（同一份设计、只把条件 10/11 对调，15 / 213 / 2517 B、CRC `0x4618`）。
2. **旧代码的死段我按意图合并了**：`black_num` 8（减速带，空段）、12（方形通道，空段）、
   14/15/16（洞口三选一）、20（U 形备选）、22（路口备选）从来没被进入过。
   v3 **没有**为它们建状态，但 `S4 过减速带` 保留了明确的两段通过判据（旧段 8/9 几乎什么都不做）：
   等「8 路全黑」**需持续 1000ms** → 等「8 路全白」 → 再等「8 路全黑」**需持续 1000ms**（三段都带超时，超时一律跳状态 5）。
   如果你要的是"减速带什么都不做、直接过去"，把 S4 的 body 缩成一块 `WAIT_MS 300` 即可。
3. **转向用"等角度到位"而不是"等固定毫秒"** ⇒ 整条流程的**耗时会比旧代码短**（旧代码 90° 只等 700ms ≈ 73°）。
   若你要和旧版逐毫秒对齐（比如为了配合场地上的固定计时），得把 `TURN_DEG` 换回 `WAIT_MS`。
4. **S0 主页的"发车"判据**：v3 假设任务是**手动启动**（按车上中键或上位机"开始"），
   所以主页 `enter` = `SET_SPEED 7000` + `SET_MODE 3`（**切循迹、车立刻跟线走**）—— 语义就是用户要的"**立即开始**，走第一个十字路口"。
   `body[0]` 那道「8 路全黑」（条件 10 `CH_BLACK`、掩码 `0xFF` = 已经骑上小阶梯）**带 8000ms 超时兜底**：
   超时**跳回状态 0 自己**（重新计时、继续循迹），**绝不往下走** —— 往下走就等于在"还没到台阶"的地方
   直接给油 + 摆台阶动作。要改成"超时就硬着头皮上"，把这一块的"超时后"改成「继续往下跑」即可（不建议）。
   若你要的是"上电/启动后先等一次全白再动"，在 S0 的 `enter` 前面插一块条件 11 `0xFF` 即可。
5. **规则文档自己标注存疑的一处**：第 9 号"大型阶梯"立面标 3.0/5.0cm，比第 3 号"小型阶梯"（总高 10.8cm）还矮，
   与"大型/小型"直觉相反（`docs/全地形机器人比赛规则与场地.md:65`）。v3 里 S14 的动作是从旧代码搬的，
   **没有**按这个存疑尺寸改过。
