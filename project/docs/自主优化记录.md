## 1. 三个"会出事"的稳定性问题（重点）

### 1.1 陀螺仪失联：角度环会以为"已经到位"，车笔直冲出去

**机理**：`Gyro_Z` / `Yaw` 是解析器写进去的全局量，一旦线断/模块死掉，它们就**冻结**成
最后一帧的值。角度环的误差 `目标 - Yaw` 于是恒为常数：如果冻结那一刻误差很小，环会判定
"已到位"（`s_law=3` 的到位锁存还会把修正直接清零），循迹串级里外层改的目标航向也跟不动，
车就照直开出去 —— 比"停下来"危险得多。

**改动**（`firmware/App/Svc/jy61p.c`、`motion.c`、`motion.h`、`Core/Src/main_app.c`）：

- `jy61p.c` 新增 `uint32_t jy61p_frame_count(void)`，**只在整帧校验通过时 +1**
  （0x53 角度帧、0x52 角速度帧都算）。这样"帧计数在涨"就是真正的活性证据，
  比"收过多少字节"可靠（噪声/半帧不算）。
- `motion.c`：进了 `MOTION_GYRO` / `MOTION_TRACE_GYRO` 以后，5ms 一拍比较帧计数；
  `>500ms` 没变化（JY61P 正常 100Hz，等于连丢 50 帧）就置
  `MOTION_FAULT_GYRO_STALE` 并 `Motion_SetMode(MOTION_IDLE)`（内部会 `Load(0,0)` 停车）。
  刚进模式给 500ms 宽限，上电/刚插模块不会误判。
- 刻意**不**在中断里发串口/RTT：`host_link_send_text` 会阻塞 ~3.4ms，在 5ms 中断里
  调用等于自伤。故障位由主循环每秒打进 RTT（`MOTION: ... fault=%u`）。
- 只对显式陀螺模式生效：任务流程（`renwu.c`）那条后台环走 `MOTION_IDLE` 分支，
  行为保持原样，避免改到 P5 的流程语义。

**离线证据**：`firmware/test/t_motion.c` 钉住了 500ms 边界（恰好 500 不触发 / 501 触发）、
进模式宽限期、"每 400ms 一帧跑 3 秒不误判"、"帧停住后再触发"、
"循迹模式（不用陀螺仪）即使陀螺死了也不停车"。

### 1.2 运动中擦 Flash：同 bank 取指停摆，5ms 控制中断被拖住

**机理**：`nvram.c` 的记录页在 Flash 最后一页（`0x0801F800`）。擦除/编程期间，CPU 从
**同一个 bank** 取指会被硬件 stall 几十毫秒（`nvram.c` 自己的擦除超时就是 50ms）。
控制环跑在 TIM6 的 5ms 中断里，指令也在同一 bank —— 于是"存一次设置"会让车顿一下冲出去。

**改动**：`nvram.c` 新增 `nvram_motion_active()`
（`Motion_GetMode() != MOTION_IDLE || SpeedControl_IsEnabled() || GyroControl_IsEnabled()`），
`nvram_poll()` 与 `nvram_service()` 在真擦写前都拦。策略是**推迟到停车后存**，
不做超时兜底（宁可不存，不能边跑边擦）。

### 1.3 `NormalizeAngle()` 在 5ms 中断里可能永久死循环

原来是无界 `while (angle > 180.0f) angle -= 360.0f;`。中断里被喂一个 `±Inf`（台架 SWD
直接改 `Yaw`、或未来某个除零）就是**永久死循环**：中断永不返回，电机保持上一拍输出。
改成非有限值直接返回 0，合法值走 `fmodf(angle, 360.0f)` 再折到 (−180, 180] —— 常数时间，
不再随角度线性变慢。

## 2. 参数/状态污染类

- **PID 状态跨任务残留**：`pid.c` 原来把 `integral`/`last_error` 放在函数内 `static`，
  没有清零入口；丢线期间积分照样累，重新压线那一拍一次性放出（猛打方向）。
  现在状态提为文件作用域 + `void PID_Reset(void)`，并且**首拍不算微分项**
  （否则 `Reset()` 之后 `Kd×error` 会变成起步冲击）。`PID_tracing.c` 在"找回线"分支
  调 `PID_Reset()`。
- **上位机可以塞 NaN**：串口 `T_PARAM_SET` 的范围检查原来是
  `if (v < min || v > max) 拒绝;` —— NaN 与任何数比较都是 false，于是**通过检查**存进参数表，
  最后一路到 `(int)` 强转（UB）。改成取反形式 `if (!(v >= min && v <= max))`，
  并加 `param_finite()` 给 `host_param_get()` / `host_param_set_local()` 兜底。
- **`jy61p.h` 去掉 `main.h`**：纯协议模块不该拖整个 HAL 进来，也让主机侧单测成为可能。

## 3. 性能 / 可观测性

- **`T_PARAM_GET` 全表 dump**：原来在一帧里同步连发 ~30 条参数报告，每条
  `board_dl_send` 阻塞 ≈1.1ms ⇒ 主循环停约 35ms（控制环在中断里不受影响，但 UI/遥测会顿、
  上位机会以为卡死）。现在每拍最多发 4 帧（`DUMP_PER_POLL`）。
- **控制中断耗时插桩**：`motion.h` / `motion.c` 用 `DWT->CYCCNT` 记每拍耗时
  （`g_isr_cyc_last/max/sum/n/over`，预算 `MOTION_ISR_BUDGET_CYC` = 5ms@170MHz），
  主循环每秒打一行 `ISR: avg=..us max=..us n=.. over=..`。
  目的是以后能一眼区分"环自己算太慢"和"环被长操作堵住"（后者真发生过：见 1.2）。
  同时把 `dwt_init()` 提到 `HAL_Init()` 之后，否则 TIM6 起跑到使能 DWT 之间的拍测不到。
- **界面陀螺仪指示灯**：`g_live.gyro_ok` 原来判"开机以来收过 >32 字节"，线一断也永远显示
  在线；改为"300ms 内帧计数涨过"。

## 7.2 `A()` 状态机：7 个分支永远进不去（**没有改它**，需要你定夺）

新工具 `tools/renwu_states.py`：不编译，只读 `renwu.c` 的文本，把 `A()` 里
`else if (... && black_num==K) { ... black_num=N; }` 抽成状态图做可达性分析，并核对
"跳过某个状态的那一支里是不是也做了同样的事"（比函数调用名）。跑法：

```
$env:PYTHONIOENCODING='utf-8'          # 不加会中文乱码
python tools/renwu_states.py           # 打印报告
python tools/renwu_states.py -Strict   # 有不可达状态就退出码 1（可当检查用）
python tools/renwu_states.py -Out out/renwu_states.txt
```

结论（从起点 0 出发只有 21 个状态可达，7 个进不去：`8 / 12 / 14 / 15 / 16 / 20 / 22`）：

- `8 / 12 / 14 / 15 / 16 / 20`：本支调用的函数（`Load`/`RW`/`Buzzer_blink`/`HAL_Delay`…）在跳过它的
  那一支里**都有** ⇒ 动作已合并进那个大分支，死掉的只是分支条件本身，无害。
- `22`（`firmware/App/Svc/renwu.c:780-799`）：本支调用 `GyroControl_TurnRight` 和
  `PID_Tracing_Timer_Start/Stop`，而跳过它的 `21` 分支（`renwu.c:755-779`）里**没有**这两个动作；
  再一看，`21` 分支里对应的那几行本来就是**被注释掉的**（`renwu.c:767-777`），末尾直接写
  `black_num=23`（`renwu.c:778`）。也就是说 21 和 22 是"同一路口的两种走法"：现在生效的是 21
  （左转 80° 后直接去 23 号十字路口），22 是留着备用的另一版（右转 80° + 倒车 + 循迹计时 1s）。
- **我没有改它**。这属于比赛动作顺序，改一个数字就让车多做一个动作，必须整车上电跑一遍才知道对不对，
  而现在主板没连；代码里又有大量注释掉的备选动作，单看代码看不出哪个是最终意图。
  要恢复 22 只需把 `renwu.c:778` 的 `black_num=23` 改成 `black_num=22`（一个字符），你说一声我就改。

## 8.1 新发现：`board_i2c_bus_recover()` 从来没人调用（严重度高）

- `firmware/Core/Src/board.c:286` 有这个函数：把 SCL/SDA 拉成 GPIO 手动打 9 个时钟 + STOP，
  再 `board_i2c_init()` 重配。但**全工程没有调用者**（只有定义和 `.map` 里的符号）。
- 后果：I2C 总线被从机拉死（从机在事务中间掉电/复位、ESD 打一下）之后，STM32 这边每一次
  `HAL_I2C_*` 都只会超时失败、**永不自愈** ⇒ 屏黑着、电流和灰度全读不到，只能断电重启。
- 为什么以前没被发现：它写得像"应急通道"，看着就该有人调；只有把调用图拉出来才看得出没接线。

## 8.2 改法：把"连续失败"变成"恢复一次"

- 决策逻辑单独放 `firmware/App/Svc/bus_health.c`（**纯逻辑、不碰 HAL**，所以能主机侧单测）：
  连续失败 `BUS_HEALTH_FAIL_LIMIT=5` 次 ⇒ 置一个"要恢复"请求；`bus_health_take(now, bus_idle)`
  只在**总线空闲**且距上次恢复 ≥ `BUS_HEALTH_RECOVER_MIN_MS=1000ms` 时才放行一次。
- `board.c` 只留三个薄封装（`board_i2c_report` / `board_i2c_watchdog` / `board_i2c_recover_count`），
  真正恢复还是调那个老函数；`main_app.c` 开机 `bus_health_init()` 清零。
- 报告点：`trace_cal.c` 的 `source_read()`（I2C 分支）与 `app_ui.c` 的 `battery_poll()`（INA226 读电压/电流）。
  执行点：`trace_cal_poll()` 的 20ms 闸门之后（用 `OLED_IsBusy()` 当空闲判据）+ `battery_poll()` 的 OLED 闸门之后。
- 诊断：RTT 每秒那行 `ISR:` 末尾多了 `| i2c recover=N`（上电以来的恢复次数），
  一眼能看出"这车一路上被总线坑了几次"。
- 为什么不做成"失败就重配"：`board_i2c_bus_recover()` 里是 9 × (1ms 低 + 1ms 高) + STOP，
  **一次阻塞约 12ms**；没插灰度模块时每帧都触发就会把主循环拖垮
  ⇒ 阈值 + 最小间隔 + 空闲闸门三个条件一起卡。
- DMA 链接没受影响（专门确认过）：`__HAL_LINKDMA(&hi2c1, hdmatx, ...)` 在另一个函数里做，
  `hi2c1` 是静态对象、`HAL_I2C_DeInit()` 不清 `hdmatx`，所以恢复后链接还在。

## 9.2 真隐患：`motor.c` 里那个不是 static 的 `abs()`

`firmware/App/Bsp/motor.c:19` 有一个自写的 `int abs(int p)`，**没有 `static`**。

## 10.1 第一轮：控制中断计时（已验）

`ISR: avg=9 us max=9~12 us n=200~201 over=0 (last=9 us) | i2c recover=0`

## 10.2 第二轮：陀螺失联看门狗（已验，含"真的会停车"）

用 SWD 屏蔽 `USART3` 中断（`w4 E000E184,00000080`，USART3_IRQn=39）把陀螺帧冻住，同时 `gyro_control_enabled=1`：

- 顺带验 `gyro_ok`：`g_live`(0x20000784) + 0x1D ⇒ 0x200007A1，实测 01 → 屏蔽 1.2s → **00** → 恢复 → **01**。

## 10.3 第三轮：I2C 总线被拉死之后能不能自愈（已验，端到端）

- 十几秒内 RTT 出现 **`i2c recover=1`**（连续 5 次读失败 + ≥1s + 总线空闲后才执行）；
- 全程 `fault=0`，且 **`ISR: avg=9us max=12us over=0` 一点没变** ⇒ 恢复那一下**没有拖慢 5ms 控制中断**

# 第五轮：角度环旋钮扫描（台架）——结论是"不动"，但摸清了机理
## 11.1 起因

第 10.4 节的图上看到：转弯过程中 `corr` 会在 **±2000 之间反复打满**，角速度跟着 0↔60°/s 起伏，
转起来"一顿一顿"。出厂基线也是这个样子，所以不是回归 —— 这一轮就是想查清它、并试出能不能既让中段更平滑、
又不破坏"不晃"的收尾。**事前定好判据：只有两头都赢才改编译默认值。**

## 11.2 机理：打满是结构性的，而且比例项单独根本起不了步

代码（`firmware/App/Svc/gyro_control.c` 的 `s_law=3` 分支）：
`rate_ref = s_ang_kp*err`（夹到 ±`s_rate_max`=110）→ `correction = s_rate_kp*(rate_ref - v)` → 再减速率微分阻尼 →
斜率限幅（`s_corr_slew*GYRO_DT`）→ 夹到 `s_corr_limit`。

- 板上用 SWD 读到的原值：`s_rate_kp=250`、`s_rate_kd=4`、`s_corr_slew=300000`（=1500/拍，**几乎等于没生效**）、
  `s_corr_limit=2000`、`s_decel=600`。
- `250 ×（速率误差）= 2000` ⇒ 速率误差超过 **8°/s** 就打满。巡航段速率误差是 30~110°/s ⇒
  **中段继电器是设计结果**，不是增益没调好（把 Kp 降到 100 也一样打满，实测翻转次数反而从 9 涨到 10）。
- 更关键：代码注释里实测的**静摩擦起转要 ≈3450**，而限幅只有 2000 ⇒ **光靠比例项永远起不了步**，
  起步实际靠的是"起转助推"（上限 `s_corr_spin`=3600）。这解释了第 10 节看到的"起步慢 200~350ms"。

## 11.4 结论：**保持编译默认值**

- 想"中段更平滑"（slew 限幅、降 Kp）**都会拿收尾的"不晃"去换**：slew 20k 把翻转从 9 降到 5，
  代价是回摆从 0.13~1.00° 涨到 **5.91°**（比基线差 3~45 倍）—— 正是用户最在意的那条。
- 想"收尾更好"（kd 4→8/12）最多把整定时间缩短约 10%，到位残差反而变大，差异还在噪声里。
- 反向教训：Kp 降到 18（=250×err 在 err>3.9° 才超过 3450 的起转阈值）会让车**一直在转**，

# 第六轮：循迹环原地 pivot 的 PID 实测（台架，2026-10-02 晚）——摸清机理，**没有改任何默认值**

> 你的要求（m12259–m12269）：车放在一小段打印线上，**只允许原地左右转**，验收就是"线一直在正中间（重心 data=4.5）"；
> 以及（m12324）：**先主动偏一个角度，再启动环，看它能不能瞬间到中间**，据此看 PID 效果并调整。

## 12.1 台架怎么做的

- 走的是真实固件的 `MOTION_TRACE` 路径（`firmware/App/Svc/motion.c:155-157` 的 `motor_tracing_pid_speed(s_base)`）：
  输出是 `l = base - pid`、`r = base + pid`。**把 `s_base` 写 0** ⇒ 一对反号 ⇒ 纯原地对转，不前进。
- 新工具：
  - `out/_tracetest.ps1`：`-Mode read`（只读）/ `-Mode pivot`（闭环）。
    pivot 支持 `-Offset/-OffsetMs/-SettleMs` 两段式：①让环自己把线停到 `4.5+Offset`（建立**已知偏置**）；
    ②断电静置（`s_mode=0/s_enabled=0/s_req=0`+TIM8 四个 CCR 写 0）让车真正停稳；③把设定值改回 4.5、
    清 PID 内部状态，再启动环 —— 这才是"先偏、再启动环"的正确做法。
  - `out/_grayread.ps1`：一次 J-Link 会话的快速只读（灰度 8 路 + `data` + `Yaw` + 帧数/丢线/模式）。
  - `out/_steptest.ps1`（第五轮写的角度环台阶）+ `_grayread.ps1` 组合起来**原地小步转着找线**。
  - `out/_tr_stats.py`：出 err0/errEnd/over/settle/rev/yawNet/reqMax，并画 `out/_tr_plot.png`。
- ⚠ 读数字义：**循迹环关着（`mode=0`）时 `data`、`trace_pos_frames`、`all_sensors_lost` 是冻结值**，
  不能拿它们当活性证据；真正会动的是 `g_live.trace[]/gray[]`。

## 12.2 出厂增益（2700/10.8/360）：小误差能"瞬间到中间"，偏置一大就转过头把线甩掉

- `out/_trc1`（静止起步，起始误差 0.756 单位 ≈ 4~5°）：**0.66 s 收到 0.032 单位，车身只转 -4.88°，无反号**（一次到位）。
  ⇒ 你要的"瞬间到中间"，在"静止起步 + 中等误差"这个量级上是成立的。
- `out/_trA_kp2700`（先把线停到 4.5+0.9，断电静置 400 ms，再阶跃回 4.5）：
  data 5.402 → 4.248，**净转 -42.01°（≈所需转角的 7 倍）**，最大左轮目标 2817 mm/s，
  跑完 `LIT=0`（8 路全白）⇒ **线被甩丢了**。同一个增益，偏置大一档就从"瞬间到位"变成"转过头"。

## 12.3 温和增益（Kp 600 / Ki 0 / Kd 90）：不甩线，但收不干净

- `out/_trC_kp600`：阶段 1 把线停在 5.359 ✓；阶段 2 收到 **4.688**（误差 0.859 → **0.188**），
  只转 **-13.03°**，最大左轮目标 **525 mm/s**，**跑完仍在线**（`LIT=3`、`lost=0`、帧数在涨）✓。
- 但残差 0.19 单位收不下去：0.19 单位时纯 P 只给 600×0.19=**114 mm/s**，低于静摩擦起转需求 ⇒ **纯 P 天生有死区**。

## 12.4 加上积分（Kp 600 / Ki 10.8 / Kd 90）：偏置阶段就把积分卷起来 ⇒ 甩线打转

- `out/_trD_kp600_ki10`：阶段 1（保持误差 3 s）线被停到 **7.769**（冲过头），
  阶段 2 **净转 -131.91°**、结束 data 2.560 ⇒ 积分 windup。与出厂增益（也带 Ki=10.8）是**同一个失效模式**。

## 12.5 机理（这轮真正量出来的两条）

1. **"转头→甩丢线→一直转"的链条**：探头看不到线以后，`data` 不再被刷新（还是上次的值），
   环就照着假误差继续输出 —— 所以只要一次转过头超过约 15~20° 车身角，就再也回不来了（只能人工放回线上）。
2. **重心↔转角是强非线性的**：各次实测"单位/度"在 **0.016~0.216** 之间乱跳（`_trc1` 0.148、`_trA` 0.027）。
   原因是车绕**两轮轴线**原地转，而探头在轴线前方 d 处：横向平移 d·θ 与转角混在同一个重心读数里。
   ⇒ 用线性 PID 去控重心，**天然容易过冲**；"调 PID"在这套几何下能拿到的收益有限。

## 12.6 结论与建议（**编译默认值一行没改**）

- pivot 场景（`base=0` + 一小段线）和前进循迹（`base=6480` + 长线）**不是同一个被控对象**；
  出厂增益是给后者调的。为了 pivot 把它改坏，等于拿比赛那套去换台架指标 —— 不划算。
- 建议做法（**要不要做请你定**）：给 pivot 单独一组 LINE 增益（例如 `s_base==0` 时切到 Kp≈600~900 / Kd≈90~135 / 小 Ki + 强限幅），
  而不是动全局默认值。
- 还没测完的（**车要放回线上**）：Kp 1200/Kd 180、Kp 1500/Kd 225、"小 Ki + 短偏置（`-OffsetMs 300`）"各 2~3 次，
  看有没有"既不甩线、残差又能 < 0.05"的组合。

## 12.7 操作教训

## 13. 循迹丢线保护：把"满舵打转"收回去（已改，**已上板验证**）

### 13.1 怎么发现的

按用户要求（m12506）不预置偏置，改成**运行中来回切换设定值**（`out/_tracetest.ps1` 新增 `-Switches '2.0@1000,4.5@2200'`，到点只写 `s_setpoint`，不清 PID、不回 IDLE、不停速度环）。出厂增益、`base=0` 原地对转（`out/_sw1_45_2_45.txt`）：

| 段 | 目标 | 误差起 → 止 | 车身净转 |
|---|---|---|---|
| 0~2.03s | 4.5 | −1.940 → **+0.019**（最小 0.001） | +1.92° |
| 2.03~4.43s | 2.0 | 追到 data 1.23 时线滑出探头 | **−131.91°（绕了 360°+）** |
| 4.43~6.0s | 4.5 | 2.097 → 2.179（已丢线，冻结值产物） | +22.65° |

第 1000 个样本切到 2.0 后命令**立刻 7200 打满**；第 ≈1210 个样本 `data` 从 1.23 跳到 6.719（线滑出探头），此后 **`reqL` 一直卡在 7200**、yaw 从 −79° → −160 → +131 → +55 → −14 …**转了 4 秒以上还在转** ✗。收尾是脚本断的电，不是它自己停的。

### 13.2 根因

`firmware/App/Svc/PID_tracing.c` 的 `motor_tracing_pid_speed()` 丢线分支：

```c
if (all_sensors_lost) {
    pid_output = last_pid_output;                    /* 保持上一次转向 */
    if (丢线 > TRACE_LOST_MS) base_speed = base_speed / 2;
}
```

"保持上一次转向"是给**瞬间丢线**（过缝、过十字）用的，但**永不衰减**：丢线前那一下正好是满舵（追大偏差必然是满舵），就会一直满舵。`base_speed/2` 在 pivot（`base=0`）下等于没做。

### 13.3 改法

新增 `#define TRACE_LOST_DECAY_MS 500U`（挨着 `#define TRACE_LOST_MS 300U`）：丢线超过 300ms 后，把保持的转向在 500ms 内**线性收到 0**；300ms 以内仍然是原行为（保持转向）。

```c
if (all_sensors_lost) {
    uint32_t lost_ms = (s_lost_since != 0U) ? (uint32_t)(HAL_GetTick() - s_lost_since) : 0U;
    if (lost_ms > TRACE_LOST_MS) {
        uint32_t over = lost_ms - TRACE_LOST_MS;
        float k = (over >= TRACE_LOST_DECAY_MS) ? 0.0f
                                                : (1.0f - (float)over / (float)TRACE_LOST_DECAY_MS);
        pid_output = last_pid_output * k;
        base_speed = base_speed / 2;
    } else {
        pid_output = last_pid_output;
    }
}
```

没有动 `motor_tracing_cascade()`（`MOTION_TRACE_GYRO`）：那里丢线保持的是 `aim`（目标航向，有界），风险等级不同，留作后续。

### 13.4 验证

- 离线：`make -C firmware` 无 warning（`text 108520 / data 356 / bss 15216`）、`run_tests.ps1` **通过 9 / 失败 0**、`check_warnings.ps1` 待处理 0、`tools/flash.ps1` 回读一致 **108884 字节 firstDiff=none**。
- 想在台架上直接造"丢线"（`out/_losttest.ps1`：把 `last_pid_output` 写成 800、`s_lost_since` 清 0、`s_mode=MOTION_TRACE`、`s_base=0`）**失败**：900 个样本里 `all_sensors_lost` **全是 0** —— 车停在路面白底上时，固件的白底基线逻辑把地面当成"线"在跟，根本不进丢线分支。⇒ 这条捷径不通，只能用真实场景验。
- 真实场景重跑同一脚本同一参数（`out/_sw2_fix.txt` / `_samples.csv`）：线在 2.31s 丢掉后，`reqL` 从 +4385 → +537 → **0**（约 0.9s 内收到 0），yaw 停在 **−83.97°** 不再动 ⇒ **车停下来了**（改前同一位置是 7200 卡死 + 绕 360°+）。短暂丢线期间仍然正常找线（2.4~4.0s 的 `data` 还在 2.2 / 1.06 / 3.5 / 1.76 / 0.59 / 4.93 之间变）⇒ 原行为没被破坏。
- ✓ **这条算"已上板验证"**：丢线之后不再满舵打转，而是松手停车。

### 13.5 顺带结论

- 大切换（4.5 → 2.0 ≈ 2.5 个单位）在 pivot 下必然甩线：探头一旦滑出去就没有再回来的信息，此后算出来的 `data` 都是陈旧值。真正的保护是"丢线就松手"，而不是把增益调大。
- `out/_losttest.ps1` 保留下来（只有加 `-Enable` 才驱电机），以后改丢线逻辑可以先用它做无动作检查。

### 14.2 先回答"为什么会一直转圈"

第一次 A1 跑飞是**我的操作失误**：忘了换增益，用上了固件里给直线循迹的默认 `LINE_KP = 2700`。pivot 下把设定值 4.5 切到 6.5（误差 2.0 个单位）⇒ 命令 = 2700 × 2.05 ≈ 5500mm/s（±7200 上限的 76%）⇒ 车猛转，探头扫过线的速度比环反应还快，线一次滑出画面（`data` 从 1.23 突跳到 6.719 就是那一刻）；此后 `data` 是冻结值，环拿着陈旧的大误差继续满舵 —— 第 13 节修掉的"丢线保持满舵"正是这个场景。

### 14.7 C 组：运动中不写 Flash

判据（`firmware/App/Svc/nvram.c:382` 起）：只有"`s_live != s_saved` 且改完静了 `NVRAM_SAVE_DELAY_MS = 1500ms` 且屏不忙 且 **`nvram_motion_active()` 为假**"才置 `s_state = BUSY`；`nvram_service()` 真写之前**再查一次**运动（`nvram.c:453`）。所以做法是：制造一个"想保存"的现场，再让车动起来，看它守不守。

工具：`out/_steptest.ps1` 新增 `-FlashArm` / `-FlashCheck`。poke 的是 **`s_saved` 的第 0 字节** —— `s_saved` 只是 Flash 那份的 RAM 镜像，而 `nvram_service()` 写的是 `write_record(&s_live)`（`nvram.c:461`）⇒ poke 它**永远不会污染标定**；同时把 `s_change_ms` 置成"现在"，让 1500ms 保存延迟从此刻起算。

实测（`out/_flash1.txt`，`-Apply -Deg 60 -FlashArm -Samples 2000`）：

| 时刻 | 状态 | 证据 |
|---|---|---|
| poke 时（uwTick `0x0033F16D`） | `s_saved[0]` 50 → **AF**、`s_change_ms` = `0x0033F16D` | `s_live[0]` 仍是 50 |
| 车原地转 60°（速度环 + 角度环都使能，历时 3.5s） | `s_state` 一直 **00 = IDLE**；收尾读回 `s_saved` = **AF**（还是 poke 值） | **一次都没写 Flash** |

## 16. 第十轮（台架+代码）：三级串级的量级核算、可在线标定、以及受控阶梯（10°/格 保持不动）

### 16.1 起因
用户把最终形态定成两种（m12856）：**正常循迹 = 三级 PID 串级（循迹→角度→速度）**；循迹中识别到障碍（全黑等）后进入固定流程，那一段**只有速度环 + 角度环（两级）**，循迹传感器只当"退出/触发"信号。"循迹环 + 速度环（没有角度环）"是旧板遗留，不伦不类。随后交代（m12871）：任务代码也要接上三级串级、三级串级要重标（从小到大），或者先算好量级。

### 16.2 先核清的代码现状（重要）
- `firmware/App/Svc/motion.c:149-176` 三种模式都挂在 TIM6 的 5ms 里：`MOTION_GYRO` → `GyroControl_Task()`；`MOTION_TRACE` → `motor_tracing_pid_speed(s_base)`（**旧两级：循迹+速度，没有角度环**）；`MOTION_TRACE_GYRO` → `motor_tracing_cascade(s_base)`（真正的三级）；`MOTION_IDLE/default` → 角度环若使能就跑 `GyroControl_Task()`，再跑 100ms 分频的后台循迹。
- **三级串级是死代码**：`Motion_SetMode()` 全工程只有 `motion.c` 内部切 IDLE 和 `main_app.c:251` 进任务前的 `Motion_Stop()`；界面里也没有选模式的入口 ⇒ 从来没人进过 `MOTION_TRACE_GYRO`。
- 比赛流程 `renwu.c` 直行段**97 处**调 `motor_tracing_pid(4.5)`（`PID_tracing.c:453-457` → `motor_tracing_pid_speed(trace_base_pwm())`）⇒ 走的正是"不伦不类"的旧两级；转弯用 `Toggle_Gyro_Control`（角度+速度两级）；后台循迹 `PID_Tracing_Timer_Start/Stop` → `motor_tracing_pid_0_task()`（也是旧两级）。
- 三级的全部实现只有末尾三行（`PID_tracing.c:417-419`）：`GyroControl_SetTargetAngle(NormalizeAngle(s_base_yaw + aim))`、`GyroControl_SetBaseSpeed(base_speed, base_speed)`、`GyroControl_Task()`；其中 `aim = -per_unit*err` 夹 ±`aim_max`（:394-399），`s_base_yaw` 在 `|err| < 0.6` 时重记（:403-408 ⇒ 等效积分、稳态无静差）。

### 16.3 量级估算（用户要的"先算好大概数量级"）
由第 12 节实测的细区几何 0.148~0.19 单位/度 ⇒ **1 单位 ≈ 5.3~6.8° 车身角**；写 `aim = -K·err` 时 `err_new = err·(1 − g·K)`（g≈0.18 单位/度）⇒ **K = 1/g ≈ 5.5°/格 是 deadbeat**、K = 10 会按 −0.8 振荡收敛 ⇒ 当时判断"固件的 10°/格 过量 1.5~2 倍，应该往 5~7 调"。

### 16.4 把它做成可在线标定（不再每档重编烧录）

## 18. 第十二轮：屏"有时候特别卡"——总线恢复把 I2C 悄悄降到 1/4 速（2026-10-05）

用户报（m26333）：「可能是因为你调试的原因……车上的这个屏幕有时候就会变得特别卡，帧率特别低」。**"有时候"三个字是本案的钥匙**：不是一直慢，是**发生过一次 I2C 恢复之后就慢、直到断电重启**。

### 18.1 先量：慢在哪一段
- 非侵入量测 `out/lagprobe.py`（每 0.5s 读 `/api/health` 的 `telem_count`、`/api/link` 的 `stats`，每 2s 读 `/api/state` 的 `telem.loop_us`）：20s 内遥测 **100Hz 稳**（min 94.9 / avg 99.9 / max 103.6 帧/s）、`drops=0`、`crc/resync` 只有开机那几次 ⇒ **主机链路没被拖慢，问题在屏那一段**。
- 固件本身就有这个量的埋点：`main_app.c:206-218` 用 DWT 夹住 `app_ui_tick(now)`，把**每轮 UI 刷新耗时（µs）**塞进遥测 p[28..29]（`host_link.c:450`）。线上原始字节核对（`out/rawtelem.py`：停桥后用 pyserial 直读 COM27 + `bridge.protocol.FrameDecoder`，只读不写）得到的关键事实：
  - `type=0x03 len=64 raw[26..31]=ff ff f2 10 09 00 ⇒ loop_us=4338`，样本序列 `4338, 10, 4074, 10, 10, 11, 10, 11…`
  - ⇒ **`app_ui_tick()` 没事可画时只要 ~10µs；真画一帧要 ~4.1–4.3ms**。RTT 里 `FRAME: update avg=823~840 us max=4189~4413 us (n≈238)` 正是这两种拍的混合（约 20% 的拍在画帧）。
  - `oled tx_done=20`/s ⇒ **400kHz + 脏列差分下屏幕约 20 帧/s**；同样内容在 100kHz 下搬运时间 ×4 ⇒ 大约 **5 帧/s**，这就是用户看到的"特别卡"。
  - 坑：`/api/state` 的 `telem.loop_us` 一度连采 60 次全是 0（页面「车上控制占用」也一直是 0.0%），与线上字节对不上；**换掉那个老桥进程（干净重启）后立刻报 4181、与线上一致** ⇒ 以后看这个量先确认桥是本次干净重启的。

### 18.2 根因 A（确定）：`board_i2c_bus_recover()` 用 100kHz 把总线"恢复"了
- `firmware/Core/Src/board.c`：`board_i2c_init()` = `board_i2c_init_hz(100000U)`（注释写着"自检固件用 100kHz，最保守"）；而 `board_i2c_bus_recover()` 结尾就是 `(void)board_i2c_init();`。
- 主程序开机只调一次 `board_i2c_init_hz(400000U)`（`main_app.c:80-83`，紧跟 `board_i2c_enable_dma()`）⇒ **每次总线恢复都把 I2C1 从 400kHz 降到 100kHz，之后没有任何代码调回去**。全工程 `board_i2c_init_hz` 调用点只有 `main_app.c:80`、`board.c:216`、`oled_diag.c:51`。
- 触发条件（不常见但会发生）：`bus_health` 连续 5 次 I2C 失败（`App/Svc/bus_health.h` `BUS_HEALTH_FAIL_LIMIT 5`，两次恢复至少隔 1000ms）⇒ 调用点在 `app_ui.c` 的 `battery_poll()` 与 `App/Svc/trace_cal.c`（灰度探头也在 I2C1 上）。`docs/自主优化记录.md` §10.3 当时手工把 PB9(SDA) 拉低验过"十几秒内出现 `i2c recover=1`"——**但没人注意到那之后总线被降到 100kHz**。
- 已排除的假设（别再查一遍）：DMA 链接没被恢复流程破坏（`:242-243` 专门确认过 `HAL_I2C_DeInit()` 不清 `hdmatx`，工程里也没有 `HAL_I2C_MspDeInit`）⇒ 恢复后 DMA 仍在，问题**只在速率**。

### 18.3 根因 B（确定）：`kk_ui` 一旦 latch 就永久不画、也没有任何人去恢复
- `Middlewares/kk_ui/src/kk_ui.c`：`kk_ui_latch_display()` 置 `display_fault=1`，而 `KK_UI_Update()` 开头 `if (status != KK_UI_OK || kk_ui.display_fault != 0U) return;` ⇒ **latch 之后屏幕再也不画、按键也不再处理**（只能断电）。latch 两条路：`OLED_GetLastStatus() != OLED_OK`、或一次传输超过 `KK_UI_DISPLAY_TIMEOUT_MS 250`。
- 恢复入口 `KK_UI_RecoverDisplay()` 一直存在（清 fault、置 dirty、把按住的键塞进 `blocked_keys`）——**但全工程没有任何调用者**。屏还在刷的人不会碰到它；一旦碰到就是"死屏"，用户嘴里的"卡"和"死"在体感上很难分清。

### 18.4 修法
1. `board.c`：新增 `static uint32_t s_i2c_scl_hz = 400000U;`，`board_i2c_init_hz()` 成功后记下实际配置值，`board_i2c_scl_hz()` 读回；**`board_i2c_bus_recover()` 改成 `board_i2c_init_hz(s_i2c_scl_hz)`**（恢复=回到原来的速率）。`board_i2c_init()` 上面补注释："只给自检固件用，总线恢复不许调它"。
2. 屏幕自愈：新增纯逻辑模块 `firmware/App/Svc/disp_heal.{h,c}`（照 `bus_health.c` 的房规：不碰 HAL、可主机单测）。`disp_heal_step(h, display_error, now_ms)`：正常就清状态；刚发现故障那一拍立刻试一次 `KK_UI_RecoverDisplay()`；之后每 300ms 试一次（`DISP_HEAL_RETRY_MS`）；第 3 次重试仍不成（`DISP_HEAL_BUS_AFTER 3`，即发现后约 0.9s）就顺手做一次 `board_i2c_bus_recover()`（调用侧保证 `!OLED_IsBusy()`），成功则 `disp_heal_recovered()` 记数。`app_ui.c` 的 `app_ui_tick()` 接住 `KK_UI_Update()` 返回码喂给它。
3. 可观测：1Hz RTT 的 `FRAME:` 行扩成 `… | i2c=%luHz disp_fix=%lu`（当前总线速率 + 屏幕自愈次数）。
4. 测试：`firmware/test/t_dispheal.c`（200039 项检查，注册进 `firmware/test/run_tests.ps1` 的 `$deps` 表 `'t_dispheal' = @('App/Svc/disp_heal.c')`）。第一次跑有 4 处失败是我把"第 3 次重试"写成了"第 4 次"——**测试反而先把语义钉清楚了**，改齐后全过。

## 19. 第十三轮：跑任务时"屏暂停刷新、都显示一" + 8 路灰度丢线保持（2026-10-05）

用户报（m26712，同一句话里三件事）：②「运行任务的过程中这个屏幕暂停刷新了，它就都显示一了」；③「你现在这个检测的八路的灰度要有能力丢线之后还能保持之前的状态，然后来找回线」。①「停在 1 这个位置时两轮速度基本一样、只有在动的过程中才有速度差」只让"先看看"，**口径待用户确认**（见 19.6）。

### 19.1 现象与第一批取证
- 真车只读（桥 8770）：`/api/state` 的 `telem.line = [1,1,1,1,1,1,1,1]`，而同一拍的 `telem.gray = [0,0,0,166,251,149,0,0]`（3 路压线、5 路空）。`/api/cal`：`ok active_set=0 quality=8`，8 路全 `ok=1 pol=0 bad=0`（例 ch0 blk169/wht277/thr223、ch4 blk215/wht363/thr289、jitter 1~2）。
- 两条数据一对照就分家了：**`gray` 有非零值 ⇒ 模拟量通路是好的（`trace_cal_analog_ok == 1`）**；而**裸口 `line` 全 1 和真实压线情况完全不符** ⇒ PA0..PA7 这根线不是有效数据源。屏幕"都显示一"就是显示走了 `line` 那一份。

### 19.2 根因（确定）：模拟量一断就回落数字口，而这台车的数字口是上拉输入
- `firmware/App/Bsp/bsp_board.c:24-45`：`bsp_trace_init()` 把 PA0..PA7 配成 `GPIO_MODE_INPUT` + **`io.Pull = GPIO_PULLUP`（:33）**，`bsp_trace_bit()` 就是 `HAL_GPIO_ReadPin` ⇒ 探头线没被驱动时 8 根全读高。
- 老 `trace_cal_level()`（`trace_cal.c` 的 `!trace_cal_analog_ok` 分支）与 `trace_cal_channel()`（`return -1`）设计成"没有模拟量就回落数字口"，理由是"界面不至于空着"。于是只要 `trace_cal_analog_ok` 掉 0（I2C 连失 5 帧后 AUTO 两个源都不通 ⇒ `TRACE_OFF_RETRY_MS 2000` 退避；或用户把「灰度接口」显式设成数字），**8 路立刻全 255/全 1**：柱子全满、底部数字全 1，看着就是"卡住了、都显示一"。
- 更糟的第二层：**任务块的判据也走同一个 `trace_cal_level()`**。`firmware/App/Svc/task_run.c:97-135` 的 `cond_ok()`：`TASK_C_LINE_LOST`（界面「探头全白」）只要有一路 `trace_cal_level(i) >= gray_thr(thr)` 就 return 0，全低才算丢 ⇒ 全 255 时**永远不成立** ⇒ 任务停在第一个「探头全白」块上再也不动。用户看到的"跑任务时屏暂停刷新"是真卡在任务里。

### 19.3 修法：界面"按住上一帧"，判定口保持诚实
1. `trace_cal.h`：新增 `#define TRACE_HOLD_MS 500U` 与三个取值口的声明（带长注释说明为什么不再回落数字口）。
2. `trace_cal.c`：`frame_compute_body()` 每出一帧 OK 帧就把 `s_fl_lvl[]` 存进 `s_hold_lvl[]`（连 `s_hold_ms`），`hold_ready()` 判"快照还在 500ms 内"；`trace_cal_channel/level` 的 `!analog_ok` 分支改成"**只有用户显式选了 `TRACE_MODE_DIGITAL` 才回落数字口**；其余按丢线走（先给按住值顶 500ms，超时 0）"；新增 `trace_cal_disp_level/disp_bit`（界面柱高/0-1，丢线时=按住值，超时=0）与 `trace_cal_held()`（1 = 现在显示的不是本帧真值）。
3. `main_app.c:185-186`：`g_live.trace/gray` 改用 `trace_cal_disp_bit/disp_level`（这两个数组只被 `app_ui.c` 读、纯显示），控制逻辑继续走 `trace_cal_channel/level`。
4. `app_ui.c`：循迹页的数据源格子（x=48）在 `trace_cal_held()` 时改打「丢线」；任务页标题行在「第几/共几」和任务名中间的空档里右对齐塞一个「丢线」（挤不下就不摆）；`draw_trace_bars()` 注释写清"底部那一行是界面看到的 0/1，控制逻辑别拿它当判据"。
- 口径（load-bearing）：**判定口不骗人**（真丢线立刻 0，任务时序不变），**界面口才按住**；断链（`analog_ok=0`）时判定也先按住 500ms，是为了"链路抖一下别让车当场跳到任务的全白分支"。

## 20. 第十四轮：跑循迹"压根跑不了"/ 停车停不下来 / 遥测 v_l·v_r 恒为 0（2026-10-05）

用户两句（m28949 / m29239）："现在跑循迹它根本就跑不了…我把它循迹的速度设置成 7200 的时候，它就直接死到这儿了，根本就不动，好像是因为你这个 PID 参数给这个速度抵消了…你测一测吧，调一下这个循迹的 PID"；"你测速不能让他一直跑啊，现在一上电他就跑，你获得完数据就赶紧让它停"。三件事一件一件查，**同一批未提交改动里一起修掉**。

### 20.1 "跑循迹不动 / 7200 不动"的根因：同模式的 SET_MODE 把速度环关死了
- 先把车上的任务解出来：任务 id 2（网页里叫「测试」）= 单状态，enter `SET_MODE p0=3`（串级循迹），body `SET_SPEED 7200` + `GOTO 0`（跳回自己）。
- `firmware/App/Svc/task_run.c` 的 `seq_begin()`（:62-79）**每次进状态都会重放 enter 块**（GOTO 自己也不例外）；而 SET_MODE 原来的实现是 `SpeedControl_Stop(); Motion_SetMode(p0);`（旧 :157-158），`firmware/App/Svc/motion.c:80` 对同模式又是 `return` ⇒ 每一个主循环拍都"先停环、再被同模式早退"⇒ 速度环永久关闭、PWM 恒 0 ⇒ 车纹丝不动。7200 那条任务正踩这个坑；id 0「常态循迹」因为 body 里有 `WAIT_COND`（最长 3s 返回"等待"、不重放 enter）所以有时能跑 —— 与他"有时能跑、7200 那条完全不动"一致。
- 修法：`task_run.c` 只在 `Motion_GetMode() != want` 时才 `SpeedControl_Stop(); Motion_SetMode(want);`；`motion.c` 同模式分支补第二道保险（非 IDLE 且速度环没开 ⇒ `SetTarget(0,0); Enable(1)`）。⇒ **"PID 把速度抵消成 0"不成立：是任务解释器把环关了。**
- 测试：`firmware/test/t_task.c` 第 12 节（`SET_MODE 3 + SET_SPEED 7200 + GOTO 0` 跑 2000 拍后 `stub_sc_stops` 不许再涨）、`firmware/test/t_motion.c` 第 4 节。变异检验：单独 stash 掉 `task_run.c` / `motion.c` 各失败 1 项，两个修复都是必需的。

### 20.2 遥测 `v_l`/`v_r` 一直是 0（他"猜速度被抵消"的另一半是假象）
- `docs/上位机通信协议.md:155-156` 早就把 offset 10/12 定义成 `v_l_mmps`/`v_r_mmps`（编码器轮速，不是 PWM），固件 `host_link.c` 却写死 0（注释"编码器还没做"）⇒ 操控页速度波形是一条 0 线。
- 修法：改用 `SpeedControl_SpeedMmps(0/1)`；`speed_control.c` 的 20ms 滑窗 + CPR/轮径换算**排在 `if (!s_enabled) return;` 之前**（:286）⇒ 环没开也有新鲜轮速。桩补 `SpeedControl_SpeedMmps`，`t_hostlink.c` 加断言。
- 真车实测（烧 117896 B 后）：`POST /api/drive {wheels, vl:1200, vr:1200}` ⇒ `pwm ≈ +3703 / −3663`、`vl/vr` 从 0/0 升到 **103/103 mm/s** ✓。

### 20.3 停车命令停不下来 + "一上电他就跑，得拔电才停"
- 现象：`/api/drive/stop`、`/api/tasks/stop`、`/api/cmd stop` 之后 pwm 仍 3200~4110、`flags.motor=true`、`vl/vr` 仍有 46~134；只能 J-Link 复位或拔电池。
- 根因：WHEELS 直给是"`Motion_SetMode(MOTION_IDLE)` + 直接 `SpeedControl_SetTarget/Enable`"（`host_ext.c:114-119`）⇒ Motion 常驻 IDLE；而 `HostExt_DriveStop()`（:71-78）只调 `Motion_SetMode(MOTION_IDLE)`（注释还假设它会停速度环），同模式早退 ⇒ **等于空操作**，速度环一直带着残留目标跑。Keep-alive 超时（`HOST_DRIVE_TIMEOUT_MS 500`）走同一条死路。
- "上电就跑"：MCU 由 USB/J-Link 独立供电（拔电机电池时 INA226 母线读到 ~0.9V 而 MCU/桥/J-Link 都活着 ⇒ 已实测），所以拔/合电池只切电机驱动电源；**只要环还武装着，合上电池车就全速跑**，只能拔电。
- 修法三层：①`HostExt_DriveStop()` 显式 `SpeedControl_Stop()`（再回 IDLE）；②`motion.c` 同模式 IDLE 也必须真停（`GyroControl_Stop(); SpeedControl_Stop();`）；③**母线低压保护**：`host_link.c` 每次 INA226 读成功就 `HostExt_NoteVbusMv()`，`HostExt_Task()` 开头的 `low_voltage_guard()` 判 —— 读数过期(>1s)或读到 0 **一律不动手**（一次 I2C 抖动不能掐跑着的车），`< HOST_VBUS_LOW_MV(3000)` 连续 `HOST_VBUS_LOW_MS(500)` ⇒ `TaskRun_Stop(); HostExt_DriveStop();`（记一次 disarm）；回到 `>= HOST_VBUS_OK_MV(9000)` 只复位监测、**绝不自己重新起步** ⇒ 拔电池即解除武装，再插上也不会自己跑。
- 测试：`t_hostext.c` 第 12 节（停车必须真停）+ 第 13 节（低压 7 步：正常/读失败/读数过期/499↔500ms 边界/同一轮不重复/电压回来不自己起步/再拔一次又动手一次）；`t_motion.c` 第 4b 节（同模式 IDLE 必须 Stop 且 `Load(0,0)`）。
- 顺手修桩的不忠实：`firmware/test/stub/host_appstub.c` 的 `Motion_SetMode()` 原来不模拟真实现的同模式早退 ⇒ 上面这个 bug 在 t_hostext 里测不出来（改了之后 mutation B 才现形）。
- 变异检验：停掉 `motion.c` 的同模式 IDLE 停 ⇒ `t_motion.c:318` 失败；停掉 `HostExt_DriveStop()` 的显式 Stop ⇒ t_hostext 5 项失败（含低压保护的两条断言）。
